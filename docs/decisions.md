# Decisions

Short records of choices that are not obvious from the specs. Change a decision by
editing its entry in a PR that the owner approves; do not add addenda.

| ID | Decision | Why |
| --- | --- | --- |
| D-01 | **v2 is a fresh build in layers; v1 is frozen at `dc6f70aa` and tagged `v1-final` by L0.1.** v1 code is a donor to read, not a base to refactor. | v1 grew to 533k lines of Rust and 61k lines of docs/audits while core paths stayed unqualified; refactoring it produced audit cycles, not features ([lessons](reference/lessons-v1.md)). |
| D-02 | One binary `eliot` (CLI, daemon, built-in plugins, hook shim, MCP). | Light install, one version, no sibling-artifact provenance checks. |
| D-03 | Plugins are separate processes speaking JSON-RPC over stdio, **one process per agent** by default; a plugin serves many agents only when its harness isolates sessions (`multi_session`: the fake, an isolating server). | A harness's tools inherit its process environment, so per-agent token, Git identity and credentials need per-agent processes; one Job per agent makes `stop --force` exact and confines a plugin crash to one agent. Any language during bring-up (R11). |
| D-04 | One SQLite file, WAL, one writer task, numbered migrations via `user_version`. | Enough for one host and millions of rows; no server; v1's schema hashing and reference-DDL checks added nothing. |
| D-05 | Events persisted with a global `seq`; streaming deltas and samples are ephemeral. | Replayable history without storing token streams. Native transcripts remain the full record. |
| D-06 | The core has no Task/Issue/review/acceptance/publication engine. | Not in the owner's statement; it was v1's largest source of code and bureaucracy. Build such workflows from rules, scripts and agents. |
| D-07 | Local trust model: one OS user owns everything; agent tokens are for attribution and routing, not security. A call without a token is the owner's; every process Eliot starts for an agent carries that agent's token (or its parent's, when the harness cannot separate them); a rule's script gets a run token that acts as the rule; a process with `ELIOT_AGENT_ID` or `ELIOT_RULE` but without its token is refused, never treated as the owner. | Agents run as the same user and can read the same files, including any "owner token"; pretending otherwise produced v1's grant/epoch/scope machinery and makes every owner command longer. Remote access (L9) will need real auth. |
| D-08 | Control model is `self` / `tree` / `project` per agent; the owner and global rules can do everything; project rules act only inside their project. | Covers "main agent commands others" and "children of any depth" with three values instead of GM epochs and handovers. |
| D-09 | Eliot Goal loop is allowed for any harness, with budgets (`max_turns`, `max_cost_usd`) and `no_progress` detection. Native goal is used where available. | Owner point 6. Supersedes v1 owner decision #3 ("no automatic re-prompt loop for OpenCode"); the risk it addressed (token ping-pong) is handled by the guardrails. |
| D-10 | Rules are TOML files (project or data dir), hot-reloaded; the owner or an agent creates one by writing a file; cron expressions are supported. Each event rule keeps a cursor committed with its firings; a new rule starts at the current `seq`; a firing that cannot be built fails and advances. | Owner point 7. Supersedes v1 owner decision #4 (configuration-only, no cron in the first slice). The cursor is what makes "no missed and no double firing" hold across restarts without activation/journal machinery. |
| D-11 | `who` is answered from Git facts (dirty files, branch diff, history), the agents' own file-change events (`agent_edits`), and advisory claims. | Owner point 10. Supersedes v1's "Git history is not ownership": it is not authority, but it is the right answer to "who works here". |
| D-12 | Claims are advisory; Eliot does not lock files. | Eliot cannot sandbox a native shell; a lock that does not hold is worse than an announcement. |
| D-13 | First real harness is Codex (app-server, Rust plugin); OpenCodex is the first proxy. | Most complete documented control protocol (threads, turns, steer, interrupt, approvals, goals) over stdio; OpenCodex targets Codex; no Node/Python needed for L2. |
| D-14 | Never automatically resend a command whose outcome is unknown — including `interrupt` and `stop`; resolve by readback or owner `cmd resolve`. | Duplicate prompts and pushes were among v1's costliest field failures; a late `interrupt`/`stop` can hit a newer turn or session. |
| D-15 | Documentation in `docs/` is specification and roadmap only; status is the roadmap checkboxes plus tests. No audit, report, inventory, packet or readiness documents in the repo. | v1 spent most of its later effort producing documents about documents. |
| D-16 | Docs are in English; the owner statement in [vision](vision.md) stays verbatim in Russian. | English is what implementing agents and vendor docs use; the original wording remains the source of truth. |
| D-17 | Harness versions are reported and displayed, never used as gates. | v1 version/provenance gates blocked work without preventing failures. |
| D-18 | Sessions started over stdio end with the daemon or their plugin (they become `lost`, `resume` continues them); `daemon stop` refuses to cut running turns unless `--drain` or `--force`; server-capable harnesses get a service mode (L7.6) so upgrades and crashes do not interrupt turns. | Simple and orphan-free first; v1 showed that controller restarts must not kill accepted work, so the long-lived case gets a real server, not detached plugin processes. |
| D-19 | Native goal and Eliot goal are independent; one of each may be active on an agent. While a native goal is active, an `on_idle` Eliot goal waits (the native goal drives); an `every` cadence still sends. | Owner decision of 2026-10-18 (v1 `agent_swarm.md` §10): the native goal is the default, the Eliot goal sends ordinary messages, and either or both may be used. |
| D-20 | Commands to one agent run strictly in order; `interrupt`/`stop` skip the line; a queued send never blocks other verbs. | v1 counterexample H18-05: `configure(max)` then `configure(high)` then `send` must not run the task on the wrong settings. |
| D-21 | `max_live` caps launches per profile, per account and per proxy; launches beyond a cap wait. Provider holds are per account. | Quotas and subscriptions are per account and several profiles share one. v1 field data: 7 of 10 lines ran on one model route that was about to be withdrawn; 429s and weekly quota windows stalled lines. |
| D-22 | **Every layer ends with an executable exit test that runs in CI (live harness runs on the owner's machine); every task lands with its tests.** There is no deferred "qualification" phase. | Owner: write the code and check that the core and the bus work, then add one harness, debug, monitor, then the rest. v1 deferred real-path checks and an audit refuted 218 of 243 "done" claims. Reverses PR #197/#198's "L0–L6 with fmt + Clippy only, tests at L7". |
| D-23 | Starting a session and giving it its first input are separate commands (launch + linked send); `session.ready` proves only the session. A harness that needs input to create a session gets it inside `agent.start`, still settled separately. | A lost start reply must never repeat the prompt, and "ready" must never be read as "the task was received". |
| D-24 | One native session (`native_scope`, `native_ref`) is one agent row for its whole history; attach, `attach --control`, detach and resume change that row. | Two rows for one session duplicate lifecycle events, rule firings and capacity. |
| D-25 | A plugin's persisted event is a request answered after commit. A replayable source sends its position as the event's `cursor`, stored in the same transaction and handed back on re-attach; a `native_id` drops repeats. No source epochs, sequence numbers or receipt tables. | Covers both lost replies and vendor replay with one column, one small table and one rule, instead of the epoch/watermark/receipt protocol of PR #197/#198. |
| D-26 | Harness processes get a minimal environment (OS baseline + named `pass_env` + profile `env` + Eliot variables); inheriting the daemon's environment is an explicit global-profile opt-in. | Inherit-all hands every secret the daemon can see to every agent and its tools. |
| D-27 | Project config may only narrow a global profile (labels, lower `max_live`, notes, setup, scratch, notices); routes, permissions, environment and accounts are global-only. | Agents can write the repository; a project file must not widen what they can do or where they spend. |
| D-28 | Custody claims only what the OS proves: Windows Job is exact; a Unix process group is `degraded` (no exact force, possible orphans) until L7.2 adds cgroups. | Process groups neither die with the daemon nor stop `setsid` escapes; v1 claimed otherwise. |
| D-29 | `--worktree --base REF` resolves REF to a commit OID at admission (no fetch) and builds from that OID; a setup step whose outcome is unknown is never rerun. | A moving ref must not change a queued launch; setup scripts are not idempotent. |
| D-30 | External write ids are ULIDs; an unknown id older than 24 h is rejected (`id_expired`) and commands are kept ≥ 30 days, so a retry is either answered or refused. Internal commands use derived ids. | Retry safety without a receipt table, floors or digests. |
| D-31 | Docs are checked by `lychee` (links and anchors) in L0.3; there are no Python doc validators and no doc-schema execution. The Store schema is checked by Rust migration tests (L1.2). | Rust-native tooling (workspace rule); tests of the real schema, not of Markdown. Reverses PR #197's `tools/ci/validate-v2-*.py`. |

## Defaults

Choices made so work never waits. Change them by editing this table.

| Topic | Default |
| --- | --- |
| L4.7 harnesses (Command Code, Kilo, Zed) | Not built until someone needs them. |
| Git identity of agent commits | Per agent (`<name>.<id>@agents.eliot`); `git_identity = "inherit"` opts out. |
| Native child without its own environment | `own_identity = false`: acts as its parent; mail notices carry the full text. |
| Selector fan-out | at most `limits.max_selector_targets` = 1,000 targets per command; no limit on the number of agents. |
| Environment | minimal; `inherit_env = true` only in global profiles. |
| Remote access (L9) | Not planned. |
| Eliot Memory OS integration | Not built until the owner asks (L9). |
