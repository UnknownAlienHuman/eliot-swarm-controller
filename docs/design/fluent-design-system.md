# Eliot Swarm Desktop — брендбук и проект интерфейса Fluent

**Версия:** 1.1 · **Дата:** 26 ноября 2026 · **Платформа:** Windows, Rust, настоящий WinUI 3.

**Назначение:** единая спецификация внешнего вида, экранов, состояний и реализации desktop-клиента Swarm Controller. Документ рассчитан на непосредственную работу агентов с существующим кодом, а не на создание нового UI-фреймворка.

**Принятое направление:** штатный Fluent WinUI 3. Material 3 Expressive заморожен и исключён из текущего задания. Его возвращение — отдельное будущее решение после развития WinUI/Reactor, а не скрытая цель этой реализации.

**База исследования:** приложенный «Eliot Swarm Desktop · Каркас интерфейса» от 24.11.2026 [U1]; первоначальная версия сверялась с `4f411a71c295434f8e61b17b13bc95e29a49eda1`. Реализационные факты этой редакции узко перепроверены по исходнику `e2a7b96f1f81713db3fceb3f66634191fc7bc638` (26.11.2026; новые ссылки [C26]–[C41]). Остальные ссылки R/C на прежней базе остаются историческими материалами исследования и не утверждают, что указанные там кодовые пути существуют сейчас. Наблюдения о сторонних приложениях принадлежат исходному исследованию, а не live-проверкам.

Числа размеров и задержек, помеченные **решение Swarm** или **цель**, — требования этого проекта. Они не являются утверждением, что Microsoft предписывает именно такие значения или что текущая сборка их уже достигает.

## 1. Задание исполнителю

Собрать спокойный, компактный и полностью функциональный Windows-клиент, в котором владелец запускает работу, читает результат, принимает необходимые решения и видит состояние всех проектов. Повседневные действия не должны требовать знания внутреннего протокола Swarm.

### 1.1. Обязательные решения

| Область | Решение |
|---|---|
| UI-стек | Rust + WinUI 3 через существующую интеграцию Reactor. Смена на web, Qt, Slint или собственный renderer не входит в работу. |
| Внешний вид | Стандартные WinUI templates, состояния и theme resources. Собственная работа — компоновка и поведение продукта. |
| Material | Не развивать его shapes, цвета, шрифты, ripple, wave, пружины и тени. История сохраняется в Git. Два параллельных оформления не поддерживать. |
| Основной экран | Беседа задачи; слева проекты/задачи, справа контекстная панель. Fleet, Inbox и настройки не превращать в постоянную приборную панель вокруг каждого сообщения. |
| Данные | Daemon остаётся единственным источником команд, состояния работы и настроек. Новая UI-база данных не нужна. |
| Готовность | Работают реальные действия, клавиатура, ввод, меню, переходы и восстановление состояния. Удачный скриншот не заменяет проверку поведения. |
| Выполнение | Один manager/worktree; конечные связанные этапы; независимая проверка. Без общего test harness, fake harness и нового framework вокруг миграции. |

### 1.2. Короткий порядок чтения для агента

Сначала прочитать текущий пункт D12, разделы 1–2 и owning spec изменяемого сценария. Затем — соответствующий экран, компонент и связанные требования к данным/вводу. Раздел 22 нужен при изменении Reactor/WinUI integration, раздел 23 — для приёмки этапа; источники из раздела 24 открывать по конкретному вопросу. Статус вести в `docs/roadmap.md`, результаты проверок — в PR. [R1], [R2], [R3], [R10]

### 1.3. Что изменено относительно каркаса

- Material заменён на native Fluent; плотность больше не подгоняется под Material touch targets.
- Меню уже нативные. Историческое утверждение о нарисованных popup не является диагнозом текущего кода. [C6]
- `agent.diff` уже возвращает настоящий patch. Changes должен использовать этот API; комментарий старого pane о его отсутствии устарел. [C12], [C13]
- Для sidebar использовать готовую группировку `chat.organization`; счётчики Inbox — существующий `daemon.sidebar`. Не изобретать `daemon.overview`. [R5], [C14]
- При недостатке ширины правая панель занимает Main с возвратом к беседе; не перекрывает composer произвольным плавающим слоем.
- Enter не подтверждает автоматически внезапно появившийся запрос или опасное действие. Решение выполняется осознанным нажатием соответствующей кнопки.
- Context и provider quota представлены отдельно. Процент контекста не является остатком подписки.
- Встроенный terminal renderer не создаётся. Первая Fluent-версия даёт процессы и открытие Windows Terminal.

## 2. Продукт и границы

### 2.1. Главная ценность

**Работа под контролем без постоянного вмешательства.** Владелец должен быстро ответить на четыре вопроса: что сейчас делают, где нужен я, что уже получилось, что мешает продолжить.

Интерфейс поддерживает автоматическую маршрутизацию и управление, а не заставляет человека вручную заменять daemon. Git и файловая система хранят результат работы; harness-сессия — заменяемый исполнитель. UI не превращается во вторую IDE, собственный coding harness или Task/Issue engine. [R1], [R2]

### 2.2. Термины интерфейса

| Термин UI | Значение | Где показывать техническую точность |
|---|---|---|
| Project | Зарегистрированный проект и его рабочая команда | Путь, manager assignment, capacity и worktrees на странице проекта. |
| Task | Видимая человеку работа, связанная с Agent | `Agent ID`, generation и профиль — в Details › Technical. Новую сущность Task в backend не создавать. |
| Chat | Беседа без исполнения в зарегистрированном проекте | Расположение в Projects может быть только организационной привязкой. |
| Agent / Worker | Управляемый Swarm исполнитель; worker подчинён manager | Native subagents отмечать `Observed`: набор допустимых действий у них иной. |
| Turn | Один ход агента | Отличать Stop turn от Stop Agent. |
| Goal | Проверяемая цель Swarm с бюджетом | Не смешивать с планом, который показывает harness. |
| Inbox | Решения и внимание владельца | Это не агентская почта. Mail остаётся отдельной деталью координации. |
| Hand off | Передача работы другой модели/сессии | Worktree, получатель и результат передачи видны явно. |
| Unknown outcome | Действие могло выполниться, но результат не подтверждён | Не заменять словами Failed или Retry. |

### 2.3. Частота действий определяет глубину интерфейса

| Уровень | Действия | Размещение |
|---|---|---|
| Постоянно | Открыть задачу, читать, Send/Steer/Stop turn, принять запрос | Sidebar, беседа, composer/decision panel. |
| Часто | Выбрать проект/модель, поставить Goal, посмотреть Changes и workers, открыть Inbox | Первый уровень шапки, composer, native flyout. |
| Иногда | Hand off, назначить manager, правила и cleanup | Контекстное меню, страница проекта, соответствующий диалог. |
| Редко | Proxy, retention, TOML, raw IDs, диагностика | Settings / Advanced / Details. |

Каждая доступная функция получает естественное место. Наличие метода API не означает отдельную кнопку в шапке или отдельную страницу.

## 3. Бренд и визуальный характер

### 3.1. Идентичность

Имя в оболочке — **Eliot Swarm**. `Swarm Controller` использовать в описании продукта и технических материалах. Сохранить существующий узнаваемый app icon; разработка нового логотипа не должна блокировать интерфейс. Не заменять icon символом случайного шрифта.

Три качества бренда:

- **Ясность:** результат и следующий шаг видны без раскрытия технических деталей.
- **Спокойствие:** движение и яркий цвет показывают значимое событие; фон и рабочие списки остаются нейтральными.
- **Точность:** неизвестные, частичные и устаревшие данные обозначаются честно; действие всегда имеет конкретную цель.

Характер — рабочий инструмент Windows: аккуратная типографика, выровненные строки, умеренная плотность, достаточный воздух между смысловыми группами. Красота строится на пропорциях и согласованности; большие декоративные карточки, градиентные заголовки, неоновые контуры и постоянное свечение не используются.

### 3.2. Темы и акцент

**Эталон проектирования — Dark. Настройка первого запуска — System.** Light и Windows Contrast themes обязательны к поддержке. Пользователь может выбрать System / Light / Dark в существующих настройках. Дополнительный редактор палитр не нужен.

Акцент принадлежит Windows. Для иллюстративной проверки допустим стандартный синий акцент ОС, но runtime не закрепляет его произвольным HEX. В High Contrast приоритет у системных цветов и native states. [W1], [W3], [W14]

Акцент используется для основного действия, выбранного раздела и активного состояния. Не окрашивать в него все иконки, заголовки и обычные строки. Успех после каждой фоновой операции не должен превращать экран в набор зелёных карточек.

### 3.3. Поверхности

| Поверхность | Оформление |
|---|---|
| Окно и sidebar | Нейтральная системная основа. Mica допустима только как уже поддерживаемый window backdrop. |
| Основная область | Читаемая theme-aware поверхность; длинный текст не помещать поверх переменного wallpaper blur. |
| Settings group / decision card | Один слой Card background и, если требуется, штатная граница. |
| Обычный ответ агента | Без отдельной тяжёлой карточки: текст в колонке чтения. |
| Сообщение владельца | Нейтральная слегка выделенная поверхность справа; не большая акцентная плашка. |
| Menu/Flyout/Dialog | Стандартная WinUI поверхность, elevation и focus handling. |

На пути к одному смысловому блоку должно быть не более двух вложенных оформленных поверхностей. Обычные layout-панели не нуждаются в фоне, радиусе и тени. Mica и Acrylic не имитировать своими слоями; системный solid fallback является корректным видом приложения. [W20]

## 4. Цвет, типографика, размеры

### 4.1. Семантические ресурсы

Ресурсы ниже — ориентир WinUI, а не собственная палитра. Их определения уже существуют в Microsoft UI XAML. Не копировать набор цветов в `tokens.json` и не подменять глобальные WinUI keys ради бренда. [W3], [G2]

| Роль | Native resource / компонент | Применение |
|---|---|---|
| Основной текст | `TextFillColorPrimaryBrush` | Содержимое и важные подписи. |
| Вторичный текст | `TextFillColorSecondaryBrush` | Путь, provider, время, пояснение. |
| Служебный текст | `TextFillColorTertiaryBrush` | Некритичные детали, только при достаточной читаемости. |
| Отключённое состояние | Native Disabled state | Не изображать недоступность только произвольной opacity. |
| Основа | `SolidBackgroundFillColorBaseBrush` | Основной непрозрачный фон. |
| Карточка | `CardBackgroundFillColorDefaultBrush` | Settings group, decision surface. |
| Граница карточки | `CardStrokeColorDefaultBrush` | Тонкое разделение поверхности. |
| Разделитель | `DividerStrokeColorDefaultBrush` | Между строками группы, без сетки вокруг каждого элемента. |
| Акцент | `AccentButtonStyle`, native selection | Главное действие и текущая позиция. |
| Ошибка / предупреждение / информация / успех | `InfoBar` с соответствующей severity | Значимые сообщения и обратная связь. |

**Ограничение Rust-слоя:** `ThemeBrush` Reactor экспортирует только часть WinUI ресурсов. Где нужный ресурс не представлен, использовать стандартный control с его встроенным оформлением либо нейтральный текст/значок. Не вводить ради вторичного оттенка новый общий движок кистей, ручную RGBA-палитру и глобальные подмены. Цвета custom-контента должны обновляться при теме без потери состояния.

### 4.2. Статусы

| Смысл | Визуальный сигнал | Пример текста |
|---|---|---|
| Идёт работа | Небольшой native progress indicator и текст; один активный индикатор на видимый смысловой блок | Working |
| Нужен владелец | Значок внимания, счётчик Inbox, короткая причина | Waiting for you |
| Успешно завершено | Нейтральное состояние; небольшой знак успеха в непосредственном результате команды | Completed |
| Ошибка | Error InfoBar либо error icon + текст | Check failed |
| Потеряна сессия | Отдельная подпись и действие восстановления | Lost · Resume |
| Неизвестный исход | Предупреждение и явный текст | Outcome unknown |
| Очередь | Нейтральный значок ожидания + причина | Waiting for a free slot |
| Удержание провайдера | Предупреждение с provider и условием снятия | Limit reached · resets at 14:20 |
| Нет данных | `—` с доступным объяснением | Context unavailable |
| Данные устарели | Возраст/состояние связи | Last read 3 min ago |

Цвет не является единственным носителем смысла. CPU activity не означает прогресс модели; отсутствие событий не означает завершение. Числа `0`, `100%` и `No changes` показываются только при соответствующем подтверждённом значении. [R8]

### 4.3. Типографика

Использовать системный WinUI font stack. На поддерживаемых Windows это Segoe UI Variable; обычный текст Regular, смысловые акценты Semibold. Не доставлять Roboto/Material fonts и не переопределять `SymbolThemeFontFamily`. [W2], [W3]

| Роль | Native type ramp | Номинальный размер | Правило Swarm |
|---|---|---:|---|
| Основной UI, строки, кнопки | Body | 14 DIP | Базовая плотность приложения. |
| Важная подпись / заголовок группы | Body Strong | 14 DIP | Не делать весь текст полужирным. |
| Вспомогательная метка | Caption | 12 DIP | Не использовать для ошибок, пользовательского ответа или главного состояния. |
| Заголовок панели / беседы | Subtitle | 20 DIP | Одна-две строки; автоувеличение высоты. |
| Заголовок страницы / Home | Title | 28 DIP | Без Display 68 в рабочей оболочке. |
| Текст сообщений | Body; межабзацный интервал решения Swarm | 14 DIP | Текст выделяется, ссылки работают; системное масштабирование сохраняется. |
| Код, команды, diff при чтении | Системный monospace, например Consolas | 14 DIP | Только содержимое кода; не менять глобальный UI font. Ограничение editable TextBox описано в §14.4 и §22.2. |

Размеры type ramp взяты из Microsoft; отступы и применение ролей — решение Swarm. Line height внутри стандартных controls не фиксировать. Для собственного Markdown допустима ориентировочная высота строки 20 DIP при 14 DIP, с автоматическим ростом при text scaling. [W2], [W3]

Текст не обрезать по высоте. Длинные строки списка сокращать ellipsis; полный путь/название доступен через tooltip и Copy. В редакторе, диалоге и критическом сообщении текст переносится. Диагностические IDs не занимают место обычных названий.

### 4.4. Сетка, отступы и геометрия — решение Swarm

В таблицах DIP означает логическую единицу XAML layout — effective pixel (epx), а не физический pixel монитора. Положение Win32-окна хранится по отдельному контракту configuration. Размеры/отступы компоновки используют шаг 4; type ramp и тонкие strokes имеют собственные правила. [W27]

| Token | Значение | Назначение |
|---|---:|---|
| `space.xs` | 4 DIP | Между тесно связанными метками. |
| `space.sm` | 8 DIP | Icon–label, строки внутри компактной группы. |
| `space.md` | 12 DIP | Padding небольшого блока, шаг формы. |
| `space.lg` | 16 DIP | Padding панели и расстояние между обычными блоками. |
| `space.xl` | 24 DIP | Отступ страницы и между разделами. |
| `space.2xl` | 32 DIP | Крупное разделение на Home; не между каждой строкой списка. |
| `sidebar.width` | 264 DIP | Открытый sidebar. |
| `reading.max` | 720 DIP | Колонка беседы и composer. |
| `page.max` | 960 DIP | Обычные Settings/Project страницы; таблицы fleet могут шире. |
| `pane.normal` / `pane.wide` | 480 / 720 DIP | Правая панель при достаточном месте. |
| `main.min_docked` | 520 DIP | Нижняя граница Main при пристыкованной панели. |
| `icon.inline` / `icon.toolbar` | 16 / 20 DIP | Сами glyphs; это не размеры hit target. |
| `content.radius` | 8 DIP | Только самостоятельные app surfaces. |
| `content.stroke` | 1 DIP | Только необходимые разделители и границы. |

Форма Button, TextBox, MenuFlyout, ToggleSwitch и других controls принадлежит их стандартным templates. Не задавать всем элементам `CornerRadius=8`, не превращать обычные кнопки в pills. Внешние углы окна принадлежат Windows.

### 4.5. Плотность

Цель для обычной однострочной строки sidebar — около 32 DIP; многострочной — от 48 DIP. Частые icon actions должны иметь область взаимодействия не меньше 32×32 DIP при базовом text size. Это **минимумы/ориентиры**, а не фиксированная высота, которая обрезает увеличенный текст.

Начинать со штатных размеров controls. Сначала убирать лишние рамки и внешние отступы; если плотности недостаточно, применять официальный `DensityStyles/Compact.xaml` только в проверенной области. Не загружать compact dictionary через новый interop только ради совпадения каждого элемента с числом 32. В выбранной версии Reactor возможность подключить dictionary проверяется отдельно. [W4]

### 4.6. Иконки и движение

Единый набор — штатные WinUI symbols / Segoe Fluent Icons. В коде одна небольшая таблица назначения glyph → действие. Числовые glyph-коды проверять по официальному каталогу; не копировать случайные значения из Material. Текст кнопки важнее редкой декоративной пиктограммы. [W23]

Не создавать собственные hover/pressed/focus анимации. Native control states и стандартные transitions достаточно. Перестановка строк, обновление метрик и каждый streaming chunk не анимируются. При отключённых Windows animation effects всё остаётся понятно. Не вычислять прогресс хода из времени или числа tool calls. [W22]

## 5. Компоненты и состояния

### 5.1. Единый каталог

В таблице указан native control или простая композиция существующих controls. Композиция `Grid + TextBlock + Button` не означает необходимость писать новый custom control с собственным input/automation/lifecycle.

| Компонент Swarm | Основа WinUI | Обязательное поведение |
|---|---|---|
| Главное действие | `Button`, Accent | Один явно главный результат в текущем блоке; во время выполнения не дублируется. |
| Обычное / тихое действие | Default / Subtle Button | Стандартные visual states; без Material state layer. |
| Действие-ссылка | `HyperlinkButton` либо корректный native link | Различать навигацию и запуск команды. |
| Icon action | Button с icon | Tooltip, доступное имя, не теряется вне hover. |
| Main action + варианты | `SplitButton` | Использовать только при поддержке нужного меню выбранным Reactor; допустимы обычная кнопка и отдельное явно подписанное More actions без псевдо-склеивания. |
| Простое меню | `MenuFlyout` | Right click / More actions / Shift+F10, Esc, возврат фокуса. |
| Выбор проекта / модели | Native `Flyout` с search и list | Один popup; bounded results; нет вложенного самодельного overlay. |
| Навигация | `NavigationView`, native items или существующая доступная list-композиция | Идентичная карта разделов, selected state и доступ с клавиатуры. |
| Иерархия задач | `TreeView` либо существующие keyed native rows | Открытие и раскрытие различаются; дочерние уровни загружаются ограниченно. |
| Текст / поиск | `TextBox`, `AutoSuggestBox` | Label, clear, сохранение ввода; ошибки у поля. |
| Многострочный ввод | Native TextBox | IME, selection, undo/clipboard, переносы; никакого canvas editor. |
| Число / выбор / булево | `NumberBox`, `ComboBox`, `ToggleSwitch`, `CheckBox`, `RadioButtons` | Диапазоны из DTO; действия не меняют смысл от оформления. |
| Разделы pane | Toggle-кнопки шапки беседы | Нажата кнопка открытого раздела; Close у самой pane. |
| Раскрываемые детали | `Expander` либо существующая доступная disclosure-композиция | Открытие не теряется от фонового refresh. |
| Settings row | Grid, текст слева, native control справа | На узкой ширине control ниже; без обязательной зависимости на Toolkit `SettingsCard`. |
| Сообщение / Markdown | Существующий parser + native текстовые controls | Сохранить выделение, ссылки, Copy и ограничения размера. |
| Code / diff | Native text, отдельные ограниченные строки/блоки | Monospace, Copy, честное сокращение; без WebView/Monaco. |
| Inline state | `InfoBar` | Не исчезает, пока требуется действие; severity определяется смыслом. |
| Подтверждение / форма | `ContentDialog` | Один dialog на XamlRoot, правильный initial/default focus, Cancel. |
| Короткий результат | Лёгкая inline/status-полоса | Undo для обратимого действия; критическая ошибка не прячется по таймеру. |
| Loading / progress | `ProgressRing`, `ProgressBar` | Determinate только при известном знаменателе; не рисовать собственные кольца. Indeterminate `ProgressRing` — только пока действие в полёте (отправка, остановка, идущее чтение или запуск), целиком и одного размера; постоянное состояние (Idle, Pending, доля квоты) — статичный знак или слова, без полых колец. |
| Empty state | TextBlock + максимум одно главное действие | Сообщает, что делать; не заполняет экран рекламной иллюстрацией. |

Все control families проверяются в фактическом Reactor API; названия выше обозначают WinUI-компоненты, а не обещают существование одинакового builder-метода Rust. Точная граница и источник API — раздел 22. [W6], [W7], [W8], [W9], [W10], [W11], [Q2]

### 5.2. Общая матрица состояний

| Состояние | Отображение и действие |
|---|---|
| Normal / Hover / Pressed / Focused / Disabled / Selected | Стандартные WinUI states. Не заменять тему на ручные переключения цвета. |
| Initial loading | Краткая loading-строка/indicator. Не показывать Empty до завершения чтения. |
| Refreshing | Уже прочитанные данные остаются; маленький индикатор. Не мигать всем списком. |
| Empty | Подтверждённое отсутствие результатов + контекстное действие. |
| No matches | Сохранить query и фильтры; предложить Clear filters. |
| Partial / Truncated | Показано N / известно M, если M есть; Load more или объяснение предела. |
| Stale | Старое содержимое остаётся с возрастом; связанные изменения проверяет daemon. |
| Error | Короткая причина, нужное восстановление; подробности и Copy отдельно. |
| Pending mutation | Зафиксирован target; повторное нажатие того же действия закрыто. Остальной интерфейс остаётся доступным. |
| Unknown mutation | Check again читает тот же command ID. Новый эффект сам не создаётся. |

### 5.3. Границы повторного использования

Допустимы маленькие helpers: icon action, field row, status line, empty state, section header, safe link. Не строить универсальный JSON-конструктор страниц, theme engine, новый event bus или собственный набор контролов. Функциональные модификации существующего native bridge удалять только после эквивалентной замены.

## 6. Окно и адаптивная раскладка

### 6.1. Состав окна

| Область | Содержание | Прокрутка |
|---|---|---|
| System title bar | App icon, название текущей задачи/страницы, системные caption buttons | Нет. |
| Sidebar | Навигация, проекты/задачи, Chats, Archive/Usage/Settings | Только растущий список; верхние и нижние действия остаются доступны. |
| Main header | Название и контекст страницы, её главные действия | Обычно закреплён. |
| Main content | Home, беседа или выбранная страница | Один основной вертикальный scroll owner. |
| Composer / decision region | Ввод или актуальное решение для этой беседы | Закреплён снизу; большой запрос получает собственную ограниченную прокрутку. |
| Context pane | Changes / Agents / Details / Terminal | Прокручивается независимо от беседы. |

Использовать системные caption buttons, Snap, системное меню, resize и drag behavior. Не рисовать собственные Minimize/Maximize/Close. Интеграция контента в title bar допустима только через поддерживаемые WinUI/window APIs; для первой версии достаточно существующего штатного title bar. [W21]

### 6.2. Правила адаптации — решение Swarm

Расчёт выполняется по client width в DIP. Не использовать физическую ширину монитора.

| Доступная ширина | Раскладка |
|---|---|
| Менее 900 DIP | Sidebar закрыт; открывается штатным navigation pane. Context pane отображается как отдельное содержимое Main; её Close возвращает к беседе. |
| 900–1279 DIP | Sidebar 264 + Main. Context pane по запросу занимает Main; состояние чата сохраняется. |
| От 1280 DIP | Возможно одновременное Sidebar 264 + Main не уже 520 + pane 480 + разделение. Если text scale/контент требуют больше, применить режим предыдущей строки. |
| От 1520 DIP | Доступен pane Wide 720 при сохранении Main минимум 520. |

Формальное условие docking: `available_width >= visible_sidebar + main_required_width + requested_pane_width + 16`. Числовые пороги — удобные исходные значения; формула и фактическое место имеют приоритет.

`Full view` разворачивает pane в Main, `Exit full view` возвращает её рядом с беседой (обе только там, где pane может стоять рядом); Close pane возвращает прежние scroll/selection/draft. Открытие pane не меняет выбранного Agent и не создаёт новый маршрут задачи. Текст header actions при нехватке места уходит в native More actions, а не сжимается до неразличимых иконок.

Поддержать существующий минимальный client size 640×480, но не пытаться разместить на нём все три колонки. Начальный размер — из сохранённых `[desktop].window`; при первом запуске ориентир 1280×800 с ограничением рабочей областью экрана. Не менять окно после первого видимого кадра. [R4], [W28]

### 6.3. Ультраширокое окно и масштабирование

Колонка беседы остаётся максимум 720; свободное место используется для pane и рабочих списков, а не растягивает строки сообщения на весь монитор. Full-view diff/fleet может использовать большую ширину. Проверить text scaling вплоть до 225%: формы складываются вертикально, строки увеличиваются, длинные кнопки переносят подпись или переходят в меню. Docking пересчитывается по фактической потребности контента в ширине, а не только по базовому breakpoint.

Window position, maximized state и размеры сохраняются существующим механизмом. Размеры client — DIP, координаты окна — по контракту текущей конфигурации; не переопределять единицы самостоятельно. [R4]

## 7. Навигация и организация работы

### 7.1. Sidebar

Порядок сверху вниз:

1. Eliot Swarm / Home; Back, Forward и Hide navigation.
2. New task; Search.
3. Inbox с числом требующих внимания; Agents с количеством работающих; Automations.
4. Projects: зарегистрированные проекты, manager и дерево задач по готовой проекции daemon.
5. Chats: задачи без организационного проекта.
6. Archive, Usage, Settings.

Не создавать второй глобальный Dashboard/Overview с теми же списками. Home — место начала работы, Agents — обзор парка, Project — обзор конкретной команды.

### 7.2. Строки

**Project row:** отдельный шеврон раскрытия, имя-ссылка на страницу проекта, компактный счётчик/manager status, More actions. Открытие страницы не меняет раскрытие дерева.

**Task row:** состояние + название; одна вторичная метка справа по приоритету: требует решения → существенная ошибка/hold → непрочитанное → изменения/возраст. Не помещать одновременно все счётчики. При фокусе и hover доступно More actions. Действия доступны и через контекстное меню.

Вложенность показывать отступом 16 DIP на уровень до разумного визуального предела; глубокая иерархия продолжает иметь корректный parent path в header и отдельный раскрываемый уровень. Не сжимать текст до нуля бесконечными отступами. Полный lineage доступен в Agents/Details.

Имена выбираются из существующей модели отображения: owner display name → заданное имя → стабильное понятное fallback. Не запускать модель для названия при каждом открытии Home. Генерация имени является отдельным backend-сценарием; placeholder не должен прыгать при каждом refresh.

### 7.3. Источник организации

`chat.organization` возвращает группы, manager assignment, transfer, totals и capacity. Desktop не ищет Git repositories заново и не вычисляет команды из одних parent links. Пагинация групп и членов обязательна; обрезанная выдача не называется полным парком. В текущем контракте группы ограничены 200 members, проекция — 1000; authoritative значения читать из DTO/spec. [R5]

**Attach to project** меняет расположение чата в интерфейсе. Оно не меняет execution scope, worktree и историю. **Continue in project** запускает предусмотренное daemon продолжение в рабочем контексте проекта/активного manager. В меню это разные команды с коротким пояснением; перенос строки drag-and-drop не должен тайно менять рабочую папку. [R5], [R7]

### 7.4. Меню задачи и проекта

| Меню | Группы действий |
|---|---|
| Task | Open / Rename / Tags; Attach/Detach placement; Continue in project при доступности; Hand off / Switch model; Goal; Move under another task; Archive/Unarchive; Stop Agent / Force stop; Delete; Copy ID / Open folder. |
| Project | New task; Manager/Transfer; Note to working agents; Open folder; Rename; Archive finished / Delete stopped; Remove from Swarm. |

Показывать действительные возможности, а не универсальный список команд для каждого состояния. Часто нужное, но временно недоступное действие остаётся с понятной причиной. Полностью неподдерживаемую функцию не выставлять как рабочую кнопку.

Archive не останавливает работающий Agent. Delete, Stop Agent и Remove project имеют разные последствия. Rename не меняет repository registration. Источник полномочий и окончательное решение — daemon. [R5], [R7]

### 7.5. Поиск и история

Ctrl+K открывает единый native command flyout: Tasks и Commands. Поиск серверный/ограниченный там, где требуется весь парк; локальная фильтрация означает только загруженные элементы и обозначается соответственно. Ввод не вызывает scan всей файловой системы или перечитывание тяжёлого status.

Enter выбирает явно выделенный результат. Для destructive команды выбор открывает штатное подтверждение, а не немедленно исполняет удаление. Back/Forward сохраняют выбранную задачу, позицию чтения, открытый pane и незавершённый ввод.

## 8. Home и запуск задачи

### 8.1. Состав

В центре — короткий заголовок `What should we build?`, выбранный project и composer. Без hero-иллюстрации и больших карточек метрик. Под composer максимум три полезных быстрых действия: продолжить последнюю задачу, заполнить промпт обзором проекта, открыть Automations. Они не отправляют запрос модели без пользовательского запуска.

Composer Home содержит prompt, attachments, Project, Workspace, Model/Effort, Access, Goal и Start task. На узком экране параметры переносятся на вторую строку; главный текст и кнопка не исчезают.

| Поле | Поведение |
|---|---|
| Project | Выбор зарегистрированного проекта или Chat. Add project открывает системный folder picker и существующую регистрацию. |
| Workspace | New worktree / Work locally по допустимому backend-сценарию. Путь показан в пояснении; права и policy берутся из проекта. |
| Model | Auto по routing role либо выбранный preset/model. Выбранное значение видно до старта. |
| Effort | Только реально поддерживаемые уровни выбранной модели; не универсальные Low/High для всех harness. |
| Access | Ask / Auto / Full в терминах текущих пресетов; объяснять итоговый режим, не подменять его более слабой операцией. |
| Goal | Goal, с которым стартует задача: Goal политики проекта (`[projects.ID.policy]`, «Goal · 3 rounds») с полями владельца поверх него, без политики — «Goal». Открывает тот же диалог Goal; в `args.goal` уходят только изменённые поля. Политика правится только в Settings › Projects, диалог ссылается туда. |
| Start task | Один admitted launch с устойчивым ID; состояние Starting/Queued и последующий переход. |
| More start actions | Queue it, Attach existing session. Skip project policy — отдельное редкое действие с обязательной причиной, когда подключён существующий backend opt-out. |

Policy opt-out предусмотрен daemon, но в проверенном desktop ещё не выведен; его подключение — отдельная строка реализации, а не уже существующее поле. Текст причины не должен попадать в обычную компактную панель до явного выбора. [R5], [C8]

### 8.2. Состояния запуска

| Состояние | Что видит владелец |
|---|---|
| Нет проектов | Add a project or start a chat. Composer остаётся полезным. |
| Папка пропала | Project folder not found; выбор другого проекта/исправление регистрации. Не запускать в случайной текущей папке. |
| Model catalogue читается | Ранее выбранное значение остаётся; индикатор внутри picker, не блок всего Home. |
| Capacity refusal | Причина и Queue it, если daemon разрешает; prompt/attachments сохранены. |
| Provider hold | Конкретный provider, условие снятия и допустимый Switch/Sign in. |
| Starting | Повторный Start закрыт; можно читать старую работу и навигацию. |
| Queued | Реальный launch intent, причина ожидания и Cancel launch. Это не очередь follow-up сообщений. |
| Outcome unknown | Check again для исходного id; не ещё один Start. |
| Admitted | Открывается конкретная задача. Late response не стирает более новый Home draft. |

### 8.3. Выбор модели

Native flyout с search, Recent, Favorites и группами harness/provider. Строка: model name, provider, current effort/availability; технический model ID — в подробностях. Не показывать всем моделям ложный Ready: stale/unknown quota и hold имеют собственную метку.

Выбор effort доступен внутри того же окна через простой native selector. Для дискретных именованных уровней предпочтительнее ComboBox/RadioButtons; slider использовать только при реальной упорядоченной шкале из capability. `Manage models` открывает Settings. Favorites и recent — существующие `[desktop]` preferences. Каталог использует `models.catalog` и его watch, а не новый локальный model registry. [R4], [R5]

## 9. Беседа, composer и журнал

### 9.1. Анатомия экрана

Шапка: название задачи, project/branch, читаемый статус. Справа — Goal, Changes, Agents, Details и More; при нехватке ширины второстепенное уходит в More. Goal всегда в шапке: без цели кнопка называется «Goal», с целью показывает её состояние («Goal · round 1 of 4», «Goal met», «Goal paused», «Goal · audit 1 of 2») и открывает тот же диалог. Пока цель не прочитана (или чтение не удалось), кнопка так и говорит («Goal · not read yet», «Goal · not readable»), а диалог читает цель сам или называет причину; неизвестное состояние не выдаётся за «целей нет» и не скрывается. В открытом чате Goal ставится вручную и из composer («+» → Goal) тем же диалогом. Без заданной цели целью служит первое сообщение; диалог показывает его как текущую цель, и владелец может заменить её своей. Changes, Agents, Details (и Terminal, пока он открыт) — toggle-кнопки, нажатые, пока открыт их раздел; подсказка каждой команды — одна строка о том, что она делает, с сочетанием клавиш. Path, PID, generation и session ID не занимают шапку.

Основная колонка состоит из сообщений владельца, журналов отдельных turns, ответов агента и редких событий жизненного цикла. Composer закреплён внизу Main, а не внутри прокручиваемой истории. Вокруг длинной беседы нет постоянно открытых карточек usage, ресурсов и координации.

| Блок | Внешний вид и поведение |
|---|---|
| Сообщение владельца | Справа, ширина по содержимому в пределах колонки, selectable text, attachments отдельной строкой. Steer и automation origin обозначаются компактной подписью. |
| Активный work log | Открытая компактная группа текущего turn; последние пять шагов видны сразу, остальные доступны через раскрытие. Это решение Swarm для визуальной плотности, не ограничение хранения. |
| Завершённый work log | По умолчанию свёрнутая строка с длительностью и подтверждёнными счётчиками. Пользовательское раскрытие сохраняется при обновлениях. |
| Ответ агента | Слева, без тяжёлой карточки; native selectable text/Markdown. Заголовки, списки, ссылки, таблицы, code blocks и Copy работают одинаково во всех turns. |
| Изменённые файлы | До пяти строк под ответом, затем Show all changes. Имя файла открывает соответствующий путь в Changes. |
| Событие сессии | Небольшая отдельная строка: resumed, handed off, context compacted. Показывать только событие из daemon/harness, не выводить его из догадки UI. |
| Ошибка turn | Краткая причина рядом с соответствующим turn; подробности раскрываются. Новый исправный turn не стирает историю ошибки. |

Summary work log собирается из уже полученных данных: `8 commands · 3 files changed`. Новый вызов модели для пересказа каждого turn не нужен. Reasoning показывается только в том виде, в котором native harness действительно отдаёт его клиенту; интерфейс не пытается реконструировать скрытое рассуждение. [C2], [C3], [R2]

### 9.2. Раскрытие шага

Command показывает имя/команду, рабочую папку, состояние и exit code, если он известен. Output — раскрываемый, selectable, с Copy. Длинный вывод ограничен текущим контрактом: `Output truncated`, а не незаметно пропавший конец.

Tool step показывает понятное имя, затем аргументы и результат по раскрытию; raw JSON не занимает основную ленту. File edit ведёт в diff. Worker step ведёт к конкретному worker. Mail, Goal, checkpoint и handoff представлены короткими событиями со ссылкой на соответствующий раздел Details.

Streaming меняет существующий блок по стабильному ключу. Появление нового token не пересоздаёт всё дерево ответа, не сбрасывает выделение и не закрывает раскрытые шаги. При копировании результатом является текст выбранного блока, а не обрезанная визуальная строка.

Live turn preview — временный best-effort draft, не committed message и не durable history. Он привязан к видимому running turn, исчезает при его завершении или смене turn/chat и заменяется committed message при readback; отсутствие или задержка preview не означает потерю результата. [C27]

### 9.3. История и прокрутка

Текущая модель истории уже имеет страницы и ограничения памяти. Сохранить её при миграции темы: 20 turns в странице, до 200 resident turns и 8 MiB resident payload; отдельные сообщения и tool rows также ограничены кодом. Это факты текущей реализации, не основание загрузить все 200 turns в один тяжёлый frame. [C3], [C4]

| Ситуация | Правило |
|---|---|
| Владелец у конца ленты | Новые события продолжают ленту; composer остаётся на месте. |
| Владелец читает выше | Не тянуть вниз. Показать Jump to latest с небольшим счётчиком новых событий, если он достоверно доступен. |
| Нажат Jump to latest | Одно прокручивание к реальному концу; при включённом reduced motion — без собственной анимации. |
| Загружается предыдущая страница | Сохранить видимый якорь и положение текста; не прыгать на начало или конец. |
| Ответ обновился после перехода в другую задачу | Обновить соответствующий cache, не текущую выбранную беседу. |
| Искомое событие вне загруженного окна | Загрузить доступную страницу либо явно сообщить границу. Не обещать переход ко всей истории без API поиска/позиционирования. |
| Данные обрезаны backend или cache | Показать причину и доступный способ продолжить чтение; не выдавать частичную историю за полную. |

Определять нахождение у конца по реальным ScrollView metrics, когда они доступны в принятой версии Reactor. Не угадывать его по отсутствию wheel event, числу сообщений или таймеру. Уже используемый native `VerticalAnchorRatio=1` — функциональная часть приложения; его нельзя удалить вместе с Material resources. [C4], [C29], [Q2]

### 9.4. Composer: точная таблица действий

Composer растёт от одной строки до разумной доли высоты Main, далее прокручивает собственный текст. Вложения, поле и команда доступны на минимальном окне; второстепенные selectors уходят в More. Под полем одна строка: + и chips (модель коротким именем, полное — в подсказке и accessible name; доступ), затем Context, команда и ▾ справа. Уже полной ширины колонки чтения chips переносятся на вторую строку, а команда остаётся справа в конце последней — как на Home; строки с одной командой не бывает. Draft принадлежит конкретной беседе и сохраняется при навигации. Attachment chip показывает состояние готовности и Remove; незавершённое чтение файла не превращается в успешное вложение.

| Подтверждённое состояние | Пустой composer | Текст введён | Существенное правило |
|---|---|---|---|
| Idle, можно начать turn | Send disabled | Send | Одна команда с устойчивой идентичностью. |
| Working, steer разрешён | Stop turn | Steer; Stop turn остаётся отдельной доступной командой | Steer адресуется текущим Agent/generation/turn. |
| Stopped / Lost | Resume, если разрешён | Resume with message, если поддерживается текущим API (кнопка остаётся «Resume», «Resume with message» — её имя и подсказка, чтобы строка не резала chips) | Возобновление не изображается обычным продолжением ещё работающей сессии. |
| Blocking approval / question | Decision panel | Draft сохранён за decision panel | Не отправлять текст в модель вместо ответа на запрос. |
| Provider hold | Причина + разрешённые действия | Ввод можно сохранить как draft | Доступность Send/Steer определяет daemon; чтение, Stop и ответ владельца не блокируются без основания. |
| Команда ещё подтверждается | Pending indicator в соответствующем действии | Новый ввод не стирать | Повторный запуск той же операции закрыт; приложение целиком не заморожено. |
| Outcome unknown | Check again | Draft сохранён | Повторный Send не является способом узнать исход предыдущего. |
| Daemon disconnected | Reconnect status | Draft остаётся редактируемым | Не показывать текст как отправленный. |

**Send и Steer различимы текстом, а не только цветом.** Если turn достоверно закончился до admission Steer, можно предложить Send as next message; при неопределённом исходе автоматическая повторная отправка запрещена. Inject note — отдельное действие More с ясным назначением; оно не подменяет Steer. Новую универсальную очередь follow-up сообщений не создавать. [R5], [C2], [C8]

Stop turn означает interrupt текущего turn. Stop Agent означает остановку исполнителя и находится в меню задачи. UI показывает реальное промежуточное состояние Stopping и результат backend; самостоятельно повторять stop, убивать процесс по локальному таймеру или обещать завершение после анимации нельзя.

### 9.5. Модель, доступ и context

Model/Effort используют общий picker из §8.3. Если выбранный harness допускает смену конфигурации только в idle, во время работы показывать причину недоступности и доступный handoff. Access запущенной сессии не меняется косметическим toggle: изменение полномочий проходит через поддерживаемый lifecycle/handoff.

Context — небольшой текст `Context 54%` или значение tokens с tooltip о scope и свежести. ProgressBar допустим только при известном denominator. При отсутствии надёжных данных — `Context unavailable`, а не 0%. Compaction отображается по native evidence. Provider quota сюда не помещать. [R8]

## 10. Решения и Inbox

### 10.1. Decision panel в беседе

Один и тот же запрос должен иметь одинаковый заголовок, варианты и смысл в беседе и Inbox. Панель содержит: что требуется, краткий контекст, варианты, необязательный комментарий и подтверждаемое действие. Технический request ID скрыт в Details.

| Тип | Представление |
|---|---|
| Approval | Понятное действие и scope: команда, файл, доступ или другой переданный native предмет. Варианты точно соответствуют запросу; `Allow once` и более широкий grant не сливаются. |
| Question | Вопрос, native radio/checkbox options по cardinality, поле собственного ответа только если разрешено. Для нескольких вопросов — явная последовательность и прогресс. |
| Unknown command/turn | Что известно, время последнего чтения, Check again и доступные owner-resolution варианты. Ни один вариант не означает скрытый повтор запроса. |
| Goal blocked | Причина, оставшийся budget, действия из daemon: изменить/продолжить/остановить, если они допускаются. |
| Provider/auth attention | Неблокирующая полоса или отдельное действие Sign in; обычный composer заменяется только при реальном блокирующем состоянии. |

При нескольких блокирующих запросах показать `1 of N` и список/переключение. Не создавать стопку модальных окон. Панель не перехватывает уже набираемый Enter; текстовый draft и выделение сохраняются. Фокус переводится к решению при явном открытии запроса, а не при любом фоновом событии. Статус Waiting for you объявляется доступно один раз.

Каждый ответ связан с исходными request/generation/revision. Если запрос уже закрыт другим клиентом, показать `Already resolved`, обновить панель и сохранить ещё не отправленный свободный текст для копирования. Не отвечать на «похожий последний запрос». [R5], [C9]

### 10.2. Страница Inbox

Шапка: Inbox, количество актуальных items, фильтр project и Refresh. Основное содержание — компактные группы вопросов/approvals, неизвестных исходов, provider holds/auth, failed/lost Agents, blocked Goals, ожидающих запусков, handoff/manager transfer и работы, требующей внимания. Категории берутся из реального payload, не из набора придуманных эвристик.

Строка: значок типа, короткая причина, task/project, возраст, recommended action. Развёрнутый item показывает основания, альтернативы и Open task. Рекомендация должна исходить из daemon; frontend не вычисляет собственный «уровень риска».

Snooze действует на конкретный subject/revision: если обстоятельства изменились, новый item снова виден. Dismiss не должен скрывать неразрешённый blocking request навсегда. Пустое состояние: `Nothing needs your attention` и возврат к задачам; без конфетти и искусственного рейтинга автономности.

### 10.3. Массовые действия

Selection mode включается явным действием. Панель показывает число выбранных items и **конкретное** действие; `Apply recommended` предварительно раскрывает состав операций. Selection ограничивается контрактом bulk API. Каждый результат остаётся per item: Applied / Skipped / Failed / Unknown.

Запуск auth `sign_in` выполняется отдельно для конкретного provider: `Apply recommended` пропускает `sign_in`, `answer` и `abandon_reservation`, как текущий desktop. Это не запрет на массовый Snooze соответствующих items, если он разрешён backend. Если revision изменился, item пропускается с причиной; интерфейс не перебирает новые варианты, пока не добьётся успеха. Массовый Stop/Delete требует обзора затронутых целей, но обычные безопасные действия не получают дополнительного общего approval ritual. [R5], [C9]

## 11. Changes, Agents, Details, Terminal

В каждый момент виден один раздел. Его выбирают toggle-кнопки шапки беседы (§9.1) и их сочетания клавиш (§19.1); повторное нажатие закрывает pane. Панель имеет заголовок — имя раздела, toggle Wide (ширина 720 и обратно к прежней одним действием; только там, где широкая pane помещается рядом), toggle Full view там, где pane может стоять рядом, и Close в конце строки; все три — стандартные команды одного размера. Ширину также задают ручка края и Settings › Panel widths; с шириной 720 содержимое переходит к широкой раскладке, как в Full view. На узком окне те же представления открываются в Main, и Close возвращает к беседе; отдельная мобильная версия поведения не нужна. Раскрываемые части (секции Details, ветви Agents) используют одну пару иконок: chevron вправо — свёрнуто, вниз — раскрыто.

### 11.1. Changes

**Назначение:** быстро понять результат, открыть нужный файл, обсудить конкретное изменение и выполнить существующую интеграцию по policy.

Toolbar: source `Uncommitted / Branch / Last turn`, `Unified / Split`, Wrap и Refresh. Список файлов: путь, состояние, additions/deletions только при известном значении. Фильтр по пути локален к уже полученному набору; частичный набор явно обозначен.

| Режим | Честный смысл по текущему API |
|---|---|
| Uncommitted | HEAD → рабочее дерево, включая staged и unstaged изменения. |
| Branch | Зафиксированный base → текущий workspace; fallback отображается из ответа. |
| Last turn | Текущий branch patch, ограниченный файлами последнего завершённого turn. **Это не точный исторический patch, созданный только этим turn.** Tooltip: `Current changes in files reported by the last completed turn`. |

Сначала читать bounded file summary, затем выбранный файл/patch по потребности. `agent.diff` уже существует: параметры Agent, optional generation, source и literal path; ответ содержит base/head, turn и файлы с hunks/text. Пределы текущего backend: до 256 KiB текста, 100 files, 1000 hunks; owned Git operation ограничена deadline. Эти пределы отображаются через `truncated`, а не обходятся бесконечной выборкой из UI. [C12], [C13]

Unified — основной режим для narrow pane. Split доступен только при достаточной ширине; при сжатии окна интерфейс переходит к Unified и объясняет причину, сохраняя выбор файла/позицию. Номера строк, `+`/`−`, подписи Added/Removed и разделение колонок дополняют цвет. В High Contrast diff остаётся понятен без зелёной/красной заливки. Monospace ограничен текстом diff. В длинном файле не строить тысячи UI nodes до показа первого фрагмента.

Binary, rename, mode-only change, deleted file, empty diff, file not found, stale generation и truncated patch имеют собственные короткие состояния. `No changes` допустимо только после успешного чтения. При Refresh сохранять выбранный файл, если он ещё существует; исчезновение файла объяснять, а не показывать старый patch под новым header.

Действия файла: Open in editor, Open folder, Copy path, Copy diff. `Ask about selected lines` вставляет путь/диапазон и текст в composer текущей задачи, затем даёт владельцу отредактировать и отправить. Само выделение строк не вызывает модель.

Review digest — раскрываемый список наблюдений о dependencies, public API, checks и изменениях вне claims, если такие facts пришли из daemon. Это не сертификат качества. Check/Integrate отображают конкретную configured operation, её условия, прогресс и результат; publishing/PR link появляются только при реальной операции/данных. Stage, Unstage, Revert и свободное переписывание agent worktree не добавлять в эту миграцию. [R6], [R7]

### 11.2. Agents внутри задачи

Scoped tree показывает manager, children и наблюдаемые native subagents. Строка: имя, роль, состояние, последнее подтверждённое действие; ресурсы раскрываются. Open task переносит в беседу выбранного управляемого Agent.

Наблюдаемый native subagent имеет метку `Observed` и доступные сведения, но не получает чужие controls Resume/Hand off/Delete. Иерархия из daemon не перестраивается по одинаковому cwd или названию. Reparent — отдельная явная операция из More, с проверкой действительного parent и возможного цикла на backend. [R5], [R6]

### 11.3. Details

Разделы — native Expander; Summary открыт, технические блоки закрыты. Пустые неприменимые разделы скрываются, а ожидаемые, но недоступные данные имеют пояснение.

| Раздел | Содержание и границы |
|---|---|
| Summary | Project, workspace, branch, profile/model, state, started/last activity; Copy paths/IDs отдельно. |
| Task | Доступный prompt/brief preview и связанные данные. Backend `task.list/get` существует, desktop caller/browser пока не найден; не подменять Task record реконструкцией из transcript. [C31], [C32], [C41] |
| Goal | Текущие Goal get/set/status UI; шапка и диалог Goal показывают default objective (A11, `default_goal_objective`), шапка, Resolve card и Inbox — audit cycles (A10, `audit_history`); task card after compaction (A12) остаётся требованием roadmap. [C36], [C37] |
| Work | Git base/head, worktree ownership, claims и интеграция. Backend/CLI предоставляет `checkpoint.list/get/restore`; desktop caller/browser пока не найден. [C33], [C34] |
| Mail | Read-only просмотр адресованной агенту координации и доставки; явная Send note/Broadcast action. Просмотр владельцем не подтверждает чтение от имени агента. |
| What went wrong | Последние релевантные failure/refusal/unknown facts, recovery action и Copy details. Один и тот же сбой не размножается в три красных карточки. |
| Activity & resources | Native process/CPU/RAM/counters с timestamp и coverage; раскрываются и обновляются только когда нужны. |
| Context | Доступные native token/compaction данные, загруженные Swarm instructions/rules по metadata; не обещать полный system prompt harness. |
| Heavy work / coordination | Только существующие применимые grants/limits/claims. Инфраструктурная переменная не превращается в editable настройку без owning API. |
| Technical | Agent ID, generation, session/profile/correlation identifiers, источники и timestamps; Copy diagnostic details без секретов. |

Backend и CLI поддерживают `checkpoint.list`, `checkpoint.get` и guarded `checkpoint.restore`; desktop пока не вызывает эти методы и не предоставляет browser или restore flow. Если добавляется desktop UI, он должен использовать exact Agent/generation и pinned checkpoint reference/OID из этих API. `var.get/set` не означает наличие `var.list`: общий браузер всех shared variables в текущем API не подтверждён. [R5], [R6], [C11], [C33], [C34]

### 11.4. Terminal

Первая Fluent-версия показывает процессы выбранной задачи: имя/команда, PID, состояние, время и ресурсы, когда доступны. Основное действие — `Open Windows Terminal` в подтверждённой рабочей папке. Временная недоступность Terminal даёт понятный результат и Copy path.

Встроенного VT renderer, собственной PTY-подсистемы, terminal input и набора фальшивых terminal tabs не делать. Исторический stdout tool command читается в work log; внешняя shell-сессия не выдаётся за живой stdin агента. [C10]

## 12. Проекты и менеджеры

### 12.1. Страница Project

Шапка: project name, короткий путь, Open folder, New task, More. Под ней одна компактная summary group: manager, состояние assignment/transfer, команда и capacity. Затем список задач; Worktrees, Coordination и Project settings доступны как разделы той же страницы. Не превращать overview в набор одинаковых больших KPI-карточек.

| Область | Содержание |
|---|---|
| Tasks | Группы Active / Needs attention / Completed / Archived по реальным состояниям, search/filter и pagination. Название, состояние, model, workspace, last activity. |
| Manager | Назначенный Agent, состояние, Open task; Claim/Assign/Launch/Release/Transfer только при допустимости. |
| Capacity | Использовано/доступно с scope. Отличать общий лимит проекта, grant manager и текущую занятость. Значение 0 трактуется по полю API, не как универсальное Unlimited. |
| Worktrees | Путь, branch/base, owner, состояние работы/cleanup; Open folder, Open task, maintenance flow. |
| Who works where | Git paths и claims с источником/свежестью. Common workspace и unattributed changes обозначаются явно. |
| Automations | Применимые rules/timers/assignments; переход в общий редактор с project filter. |
| Policy | Короткое summary checks/formatter/access/publishing; Edit project settings ведёт к единственному редактору. |

Для sidebar использовать `chat.organization`: он уже возвращает group headers, manager assignment, team totals/capacity и transfer; строки задач подгружаются страницами. Общая численность и загруженная часть различаются. Не выполнять `agent.get` для каждой строки ради счётчика и не опрашивать каждый Git worktree при раскрытии sidebar. `project.overview` существует для подробного чтения; его наличие не требует дублировать все сведения на главном экране. [R5], [C14]

### 12.2. Назначение и смена manager

Если manager не назначен, показать одну полезную строку `Choose a manager` с существующими кандидатами и Launch manager. Конкурирующие root Agents отображаются как конфликт assignment; UI не выбирает победителя по времени последнего сообщения.

Transfer показывает source, successor, workspace, brief и условия перехода. После запуска — реальный stage/progress, а не неопределённое декоративное вращение без текста. Если source ещё дренируется, successor не запускается повторно из-за истёкшего UI timeout. Частичный/unknown outcome остаётся доступен для readback и owner resolution. [R5], [R6]

`Attach to project` переносит строку в организационную группу. `Continue in project` меняет дальнейшее выполнение через поддерживаемый workflow под активным manager. Диалог второго действия показывает destination и что произойдёт с текущей работой. Отображение в новом разделе sidebar само по себе не означает переноса worktree или прав сессии.

### 12.3. Координация и project actions

`Note to project agents` открывает форму с получателями и текстом; Send выполняется только явно. Показывать per-recipient outcome, если он предоставлен, и не выдавать постановку mail в очередь за чтение агентом. Claims объясняются как координация владения, а не гарантированная файловая блокировка.

Project More: Rename, Open folder, Archive finished, Delete stopped по условиям backend, Remove project. Remove project удаляет регистрацию, а не silently удаляет checkout. Точные последствия операции всегда формируются по фактическому API/maintenance plan. Путь/branch доступны для копирования без открытия advanced страницы.

## 13. Обзор Agents

Это обзор всей команды для диагностики и переключения, а не основной экран приложения. Шапка: Agents, search, project/state/model filters, grouping и Refresh. Один ряд компактных summary counts допустим, если числа пришли из fleet projection и их coverage указан. Остальная площадь — списку.

| Колонка | Правило |
|---|---|
| Task / Agent | Главная, гибкая ширина; parent/worker hierarchy или grouped mode. |
| State | Working, waiting, idle, stopped, lost, failed, unknown — без объединения несовместимых состояний. |
| Project / workspace | Короткое имя, полный путь в details/tooltip. |
| Model | Реально используемый profile/model; pending switch не показан как уже применённый. |
| Last activity | Возраст и источник; точное время по раскрытию. |
| Resources | CPU/RAM/process count только если доступны и измерены; при узком окне в details. |
| Attention | Открывает соответствующий Inbox item или задачу. |

Выбор строки открывает краткий detail или задачу; double-click и Enter имеют одинаковую основную цель. Secondary actions доступны через native context menu и keyboard menu key. Активные значения не переставляют строки каждую секунду: sorting меняется по явному выбору, а обновления сохраняют фокус и положение.

Autonomy за 24h/7d — дополнительное чтение по запросу: реальные counts, вмешательства, holds, outcome и coverage. Универсальный процент «агент автономен на 98%» без определённого backend показателя не вводить. Cloud MCP owner не является локальным процессом/Agent; observed native subagents имеют отдельный тип строки. [R2], [R8]

## 14. Automations и Scripts

### 14.1. Организация страницы

Два раздела: **Automations** и **Scripts**. На Automations — фильтры project/type/state и список с Name, Trigger, Scope, Enabled, Next run и Last outcome. Next run показывается только для расписания, где backend действительно вычислил его; rule на event не получает выдуманную дату следующего запуска.

Типы различаются: event rule, timer, recurring assignment. Один и тот же rule не редактируется независимо на странице проекта и в Settings: оба перехода открывают этот редактор. Текущее приложение уже показывает assignments/rules/timers и отдельные действия, но полный редактор ниже — **задание реализации**, а не описание готового GUI. [R7], [C15]

### 14.2. Редактор automation

Форма использует обычные native controls и раскрывающиеся дополнительные параметры. Никакого node graph и отдельного визуального языка программирования.

| Группа | Поля / поведение |
|---|---|
| Name & scope | Название, enabled, project или конкретный допустимый scope. |
| When | Event type либо поддерживаемый timer schedule. Только grammar и trigger types из owning spec. |
| Only if | Типизированные условия, которые daemon действительно умеет проверить. Не редактор свободного исполняемого JS. |
| Do | Разрешённое action: запуск/dispatch, message, check/integrate, script и другие фактически поддерживаемые router actions. UI подставляет форму по выбранному action. |
| Repeat & limits | Interval/cron/once, time zone и ограничения только в поддерживаемой форме; ясно показать итоговое расписание. Не заявлять RRULE, если его нет в API. |
| Advanced | Source/revision, binding и дополнительные поля без дублирования базовой формы. |

Save валидирует и сохраняет; он не исполняет rule/script. Validation error привязан к полю и не стирает draft. Если после hot reload остаётся last valid version, показать `Changes are invalid; previous version is still active` с доступом к ошибке. Disabled и invalid — разные состояния.

Run now — отдельное осознанное действие timer через существующий `timer.run`, с исходной командной идентичностью и результатом admission. Для settings-managed assignments текущие действия — Pause/Resume/Edit; универсальный Run now для assignment не обещать без соответствующей операции. `rule.catch_up` — ограниченная повторная обработка подходящих событий, а не просмотр run history. Перед запуском такого действия показывать его реальный scope и ограничения. `rule.get` даёт последнее outcome/refusal/cursors; отдельного `rule.history` в проверенном API нет. Полную вкладку History не рисовать до reader API. [R5], [R7]

### 14.3. Recurring assignments

Карточка: имя, brief/folder source, project/workspace, role/routing, schedule/concurrency, paused state, последнее outcome. Edit открывает соответствующую typed form; Pause/Resume не удаляет configuration. Очередной запуск выбирает допустимую модель через daemon routing, а не сохраняет случайный прошлый model ID как вечный default.

Brief directory, policy и пределы исполнения показываются до включения assignment. Errors/unknown outcome не создают второе задание по таймеру UI. Configuration раздел содержит ссылку на тот же редактор; поддерживать два независимых набора полей не нужно.

### 14.4. Scripts

Список ограничен разрешёнными roots из backend; путь, тип, revision, состояние чтения. Пустая страница с `next_cursor` означает, что нужно продолжить pagination, а не что scripts отсутствуют. Не сканировать произвольный диск из desktop.

Редактор использует native multiline TextBox, Save/Reload и indication of unsaved changes. В проверенном Reactor snapshot `font_family` есть у TextBlock, но отсутствует у TextBox: editable поля Scripts/TOML сохраняют штатный UI font, а code preview использует scoped monospace. Для полноценного редактирования кода доступен Open in editor; для больших файлов — bounded preview. Это явная граница первой поставки, а не повод глобально менять шрифт всех полей. Сохранение связано с исходной revision; конфликт сохраняет локальный текст и предлагает загрузить новую версию для сравнения. Save не запускает script. Run допускается только через существующий разрешённый daemon operation; не вводить прямой shell executor в UI. [R7], [Q2]

## 15. Settings, модели и провайдеры

### 15.1. Общая форма

Settings заменяет обычную навигацию на список категорий; Back to tasks возвращает прежнюю задачу/scroll/draft. Справа — одна колонка групп, до 960 DIP, с короткими пояснениями. На узком окне selector категорий и Back заменяют постоянный второй sidebar.

Строка настройки: слева Label и короткое Description, справа native control; при увеличенном тексте control переносится ниже. Связанные строки объединяются одной поверхностью. Каждая настройка имеет один canonical editor, даже если входов к нему несколько.

Одиночные простые preferences могут сохраняться немедленно с реальным pending/error feedback. Многошаговые формы routing/project/automation имеют Save и Cancel. Не смешивать silent autosave части формы с общей кнопкой Save, которая создаёт ложное ощущение транзакции.

### 15.2. Полный состав категорий

| Категория | Содержание | Существенное правило |
|---|---|---|
| General | System/Light/Dark; startup Home/last task при наличии typed preference; default access; доступные preferences беседы; shortcuts | Новые preferences добавлять в существующий typed `[desktop]`, а не local JSON. |
| Models & presets | Presets, model catalogue, effort, visibility, favorites/recent, provider availability | Только native capabilities; модель и preset различаются. |
| Routing | Roles, ordered candidates, failover, reserve/holds по действующему контракту | Порядок явный, Up/Down доступны клавиатурой; drag-only редактор запрещён. |
| Owner rules | Owner instruction paths / defaults, чтение и переход к поддерживаемому editor | Не обещать изменение внутреннего vendor system prompt. |
| Projects | Регистрации, paths, checks/formatter, policy, permissions, publish/integrate configuration | Project Check имеет один редактор и действительный command/timeout/budget. |
| Worktrees & cleanup | Root/placement settings, retention по поддерживаемым полям, plan/apply, исключения и результат | Удаление проходит через backend plan, не файловые операции desktop. |
| Attention | Существующие no-progress/no-code/children/turn/other thresholds и соответствующие enabled policies | Подпись содержит единицу, scope и смысл zero/default из схемы. |
| Capacity внутри Project / Usage | Global/project/manager limits, reservations/priorities и применимые quotas по действующему владельцу поля | Отдельной Settings page сейчас нет; не создавать её ради дублирования. Не приравнивать capacity slots к provider token quota. |
| Accounts & proxies | Provider auth/status, Sign in; разрешённые endpoints/proxy configuration | Credentials обслуживает vendor/native flow. Secrets не выводятся в diagnostic copy. |
| Cloud MCP | Remote owner connection/configuration и состояние | Не притворяется локальным Agent/PID. |
| Daemon | Версия/связь, data directory, restart policy continue/hold, log level, chats folder, Stop Swarm | Stop/drain/force имеют разные последствия и результат. |
| Retention & storage | Поддерживаемые retention settings, размер/состав по запросу, cleanup | В проверенном roadmap нагрузочная qualification retention ещё не подтверждена; дизайн не закрывает этот пункт. |
| Advanced | Config revision/history, TOML view/edit/validation, diagnostics | Один `<data_dir>/config.toml`; typed forms и TOML не расходятся. |

Ряд названий здесь объединяет существующие разделы ради понятной навигации. Это не разрешение выдумать поля, которых нет в DTO. Поле без backend support не показывать как рабочее: сначала добавить bounded typed configuration и save/read либо оставить capability вне текущей поставки с точным статусом в roadmap. [R4], [C16]

### 15.3. Preset и routing

Preset editor: name, harness/provider/model, effort и поддерживаемые параметры; summary итогового поведения. Duplicate создаёт новый draft, Delete показывает фактические ссылки/ограничения, если их возвращает backend. Hidden preset не должен незаметно ломать уже активного Agent.

Routing editor показывает роль и упорядоченный список кандидатов с состоянием availability. Связанные hold/failover/reserve правила объясняются рядом. UI не запускает отдельные model probes на каждое раскрытие строки и не оплачивает запросы модели ради проверки оформления. Unknown availability не переименовывать в Available. [R4], [R5]

### 15.4. Save, validation и конфликт

При чтении формы хранится revision. Validate/Save идут через текущий settings protocol; restart-required показывается отдельно от успешного сохранения. Если daemon отклонил старую revision, локальный draft остаётся; `Reload current` явно предупреждает о замене draft, `Copy my changes` позволяет сохранить текст. Никакого silent last-write-wins.

После Save UI показывает подтверждённое значение из canonical response/readback. Поздний ответ формы, закрытой до завершения Save, не должен переписать другой открытый editor. Ошибка транспорта после mutation — повод проверить исход, а не повторить Save новым command ID. Не расширять endpoint общим JSON map, если typed contract уже определён. [R4], [C16]

### 15.5. Auth и внешние программы

Sign in показывает выбранный provider и реальное состояние Queued / Opened / Cooldown / Unknown / Completed. Desktop выполняет только предусмотренный фиксированный native sign-in flow; ввод credentials происходит у vendor. Закрытие external window не считается подтверждённым входом без проверки daemon.

Повторное нажатие не создаёт несколько одинаковых sign-in процессов; active request можно проверить. Sign in доступен из Accounts, model picker hold и Inbox как одна операция с одним состоянием. Пароли/ключи нельзя включать в Copy details, toast или обычный журнал UI. [R2], [R5]

## 16. Usage и ограничения

Usage отвечает на вопросы: какой provider доступен, что расходуется, где сработал limit и что можно сделать дальше. Это не общий финансовый dashboard и не продолжение Context indicator.

| Блок | Содержание |
|---|---|
| Provider summary | Provider/account, window/limit, used/remaining, reset time и freshness, если они реально известны. |
| Holds | Конкретная причина: rate/quota/auth/model availability; affected scope, clear/reset condition, допустимые Sign in/Switch/Refresh. |
| Work usage | Agent/project usage с единицами, native source и coverage. Partial/estimated значения помечены. |
| Routing impact | Какие роли/candidates сейчас ограничены; ссылка в Routing. |
| Capacity | Отдельный краткий блок slots/reservations при необходимости; не складывается с tokens/cost. |

В sidebar строка Usage следует за текущей работой: открытый чат использует harness своего Agent; проект — harness с наибольшим числом работающих там Agents, а при равенстве или отсутствии работающих — harness самого недавно активного Agent; на остальных страницах — самый загруженный harness в fleet, затем harness следующего запуска composer. До первого полного чтения квоты строка не показывает значение. После чтения она показывает только квоту или hold выбранного harness, либо `quota unknown`, если его окно недоступно; квота другого harness не подставляется. Для открытого чата с неизвестным harness число не показывается. Flyout перечисляет каждый harness один раз; подробности и управление находятся в Settings › Usage. Время сброса берётся из полученного timestamp, а истечение времени само по себе не превращает unknown в unlimited. [C26]

USD показывать только при достоверной денежной единице/методике backend. Native cost units или tokens нельзя подписывать `$`. По model context без capacity denominator показывать абсолютное значение или unavailable. Unknown, unsupported, stale и zero отличаются. Read/Refresh не инициирует платный inference. [R4], [R5], [R8]

## 17. Archive, cleanup и восстановление

### 17.1. Archive

Archive — организация истории. Страница содержит search, project filter, name/state/last activity и Restore. Архивирование не является Stop Agent и не удаляет worktree. Если состояние не допускает archive, UI объясняет отказ и показывает подходящее действие.

После успешного archive — короткое inline сообщение с Undo, пока обратная операция допустима. Удаление относится к другой команде и не находится на месте Undo. Restore возвращает задачу в прежнюю допустимую группу. Явная Owner-команда Resume может продолжить archived Agent без предварительного unarchive; Send и остальные Resume требуют неархивированного target. [Контракт archive после #1215](https://github.com/UnknownAlienHuman/eliot-swarm-controller/blob/a9c47ddf4e1d99ea87ea90ce92e81a91c72a1433/docs/spec/api.md#L1311)

### 17.2. Managed worktrees и cleanup

Один экран показывает inventory workspaces и отдельно предлагает cleanup. Строка worktree содержит project, path, branch/owner и состояние. Факт «агент завершён» сам по себе не разрешает удалить директорию с результатом.

Последовательность cleanup:

1. Выбрать scope и запросить daemon plan.
2. Показать safe candidates, kept/blocked items и причины; размер только если он измерен.
3. Выбрать конкретные safe items либо `Clean all safe items in this scope`.
4. Подтвердить **конкретный scope и последствия**, затем запустить существующий apply job.
5. Читать durable status/progress; показать removed/kept/failed/unknown и дальнейшее действие.

Текущий plan ограничен 64 candidates на страницу; continuation связан с snapshot/filters и может устареть. `cleanup.apply` применяет выбранную страницу, `cleanup.apply_all` уже умеет полный owner sweep для project/all; `cleanup.status` возвращает прогресс. Desktop сейчас ведёт пользователя по страницам, поэтому Fluent должен подключить существующий `apply_all` для полного safe scope, а не написать frontend loop удаления файлов. SelfTree не представлять как допустимый scope `apply_all`. [C17], [R5]

Устаревший plan означает Refresh plan, а не незаметное изменение списка под уже данным подтверждением. Страница показывает условия eligibility и итоговые per-item причины; слово Safe относится к policy daemon, а не к обещанию UI, что «там точно ничего нужного». Закрытие окна прогресса не отменяет job: при возврате читается тот же job ID.

### 17.3. Delete и Remove

| Команда | Что обязательно объяснить |
|---|---|
| Delete task/Agent | Фактические удаляемые записи/истории/артефакты и ограничения текущего backend. Не добавлять обещание очистки vendor history, если операция её не делает. |
| Remove worktree | Точный path/branch, owner и eligibility; busy/dirty/retained причины. |
| Remove project | Регистрация и влияние на открытые задачи; checkout остаётся на диске по текущему контракту. |
| Delete rule/preset | Конкретный объект, known references и validation result. `script.delete` в текущем API не найден: кнопку удаления script не добавлять на основании одного существования editor. |
| Stop Swarm / Force stop | Отличие drain от принудительной остановки и результат для текущей работы. |

Обычное Remove attachment или Clear filter не требует destructive dialog. Подтверждения используются там, где реально меняются данные/исполнение; текст кнопки называет операцию, а не `OK`.

### 17.4. Daemon recovery

При недоступности daemon sidebar и уже загруженная беседа могут оставаться read-only с возрастом данных. Draft остаётся редактируемым. Главный recovery block содержит причину и доступные действия: Retry connection, Start daemon, Open logs/data folder, Repair settings либо Choose data directory. Не показывать все способы одновременно, если причина уже однозначна.

Если владелец намеренно остановил Swarm, UI не запускает его снова по обычному reconnect timer. Повторное подключение восстанавливает subscriptions/cursors и подтверждает snapshot; cached Running не считается доказательством живого процесса. Gap в event stream требует resnapshot, а не догадки о пропущенном событии.

Unknown command восстанавливается чтением исходной операции. Owner resolution выбирается из допустимых вариантов daemon с сохранением идентичности. Последний успешный action другой generation не разрешает предыдущий unknown. [R2], [R5]

## 18. Диалоги и сквозные сценарии

### 18.1. Единый стандарт диалога

Native ContentDialog используется для короткого решения/формы. Большой editor открывается страницей, выбор модели — Flyout, контекстные действия — MenuFlyout. Один dialog содержит одну цель, заголовок действием, короткий контекст, поля и явно названную primary action.

Для сложного выбора, approval и destructive action нет универсальной Enter-кнопки по умолчанию. Cancel/Close доступны клавиатурой; закрытие не теряет несохранённые изменения без пояснения. В диалоге достаточно места для multiline error, увеличенного текста и длинного пути. Рабочая область окна ограничивает максимальный размер, содержимое прокручивается. [W9], [G1]

| Диалог | Обязательные поля и проверка |
|---|---|
| Add project | Folder, display name при необходимости; найденная регистрация/ошибка path; результата регистрации достаточно для появления в navigation. |
| Rename | Текущее имя, validation, Save; не смешивать display name с переименованием branch/каталога. |
| Tags | Существующие tags и bounded editor; серверные ограничения, conflict revision. |
| Attach to project | Destination + явная подпись «изменяет расположение в списке»; не обещает смену workspace. |
| Continue in project | Destination manager/workspace и результат дальнейшего исполнения; отдельная команда. |
| Hand off / Switch | Source, destination model/profile, transfer brief/message choices, workspace; затем progress/readback. |
| Reparent | Действительный parent, кандидат и последствия иерархии; отказ при неподходящем состоянии/цикле. |
| Goal | Текст цели, реальный check, budget/round limits в исходных единицах; Save/Pause/Resume/Clear по allowed actions. |
| Restore checkpoint | Полученный checkpoint, exact target head/workspace и backend preconditions; не произвольный Git reset. |
| Stop/Delete/Cleanup | Конкретный объект/scope и действительные последствия; primary action не default Enter. |
| Config conflict | Что изменилось, сохранить локальный draft/Copy, Reload current; не молчаливый overwrite. |

### 18.2. Сквозные пути, обязательные к завершению

| Сценарий | Полный путь владельца | Признак завершения |
|---|---|---|
| Новый проект и задача | Home → Add project → prompt/model/workspace → Start → admitted task | Prompt сохранён в истории, исполнение относится к выбранному проекту/Agent. |
| Длинная работа | Work log → читать выше → новые события → Jump to latest → результат → Changes | Чтение не прыгает, diff настоящий, draft не исчезает. |
| Нужен ответ владельца | Inbox или inline decision → вариант/ответ → submit → resolved | Одна revision-bound команда; оба представления синхронны. |
| Работающая модель требует корректировки | Ввод → Steer → applied/rejected/unknown | Статус связан с тем turn, которому адресовано действие. |
| Stop turn с fallback | Stop turn → Stopping → native result либо Agent stopped | Итог явно объясняет, прерван только turn или остановлена сессия. |
| Provider исчерпал лимит | Hold → прочитать причину → разрешённый Sign in/Switch/Wait → новый подтверждённый state | UI не расходует inference для снятия визуального hold. |
| Projectless chat становится работой проекта | Task menu → Continue in project → destination → handover | Отличимо от организационного Attach; нет дубликата manager/запуска. |
| Замена manager | Project → Transfer → reviewed destination/brief → progress → assigned successor | Старое/новое владение и незавершённый transfer видны точно. |
| Автоматизация | Automations → typed editor → validation → Save → Run now отдельно → outcome | Save не запускает работу, результат не выдуман из закрытия формы. |
| Конфликт настроек | Edit → concurrent revision → Save refusal → preserve draft → reload/reapply | Нет потери локального текста и скрытого перезаписывания чужих изменений. |
| Потеря связи | Command pending → disconnect → reconnect → Check again | Нет повторной mutation и ложного Success. |
| Очистка | Scope → plan → reviewed safe selection/full scope → job → status | Удаление принадлежит daemon, progress переживает закрытие панели. |

### 19.2. Focus и assistive technology

Порядок Tab следует видимой структуре. Списки используют native selection/arrow navigation, а не сотни несвязанных tab stops. Фокус виден в обеих темах и Contrast themes; его outline не обрезан parent panel.

После закрытия меню фокус возвращается к инициатору. После закрытия pane — к кнопке открытия/прежнему Main. После удаления строки — к следующей подходящей строке или заголовку списка. Фоновый event не перехватывает фокус. Selected task и focused row — разные состояния.

Icon-only control имеет Automation name и tooltip. Form label связан с полем; validation error доступен screen reader. Статус отправки/ошибки объявляется один раз; токены streaming и постоянно обновляющийся CPU не создают бесконечные объявления. Tooltip не является единственным местом критического предупреждения.

Custom text/diff/Markdown сохраняют выделение, Copy, семантику ссылок и доступное чтение. Если элемент Reactor не предоставляет нужное свойство accessibility, это конкретный API gap для compatibility этапа, а не повод заменить native Button кликабельным Border. [W13], [W16]

### 19.3. Масштабирование и touch

Проверить DPI 100/125/150/200%, перенос между мониторами и отдельный Windows text size вплоть до 225%. Это разные параметры. При росте текста шапка и строки растут, control переносится ниже label, docked pane уступает место Main mode. Номинальные 32/48 DIP не являются фиксированным clipping height.

Компактные hit targets из §4.5 рассчитаны на мышь/клавиатуру. Для активного touch-сценария сохранять штатную плотность controls и доступные области нажатия; Microsoft рекомендует ориентир 40×40 effective pixels. Не уменьшать системный Button до размера его 16-DIP иконки. Основной UI не требует hover для обнаружения единственного способа выполнить действие. [W24], [W25]

### 19.4. Язык и microcopy

В этом проекте labels приведены на английском, чтобы соответствовать текущему desktop. Хранить пользовательские строки единообразно и пригодными к будущей локализации; не начинать параллельный i18n framework в миграции. Русская локализация, если включается, покрывает весь сценарий, а не отдельные кнопки.

Sentence case, конкретные глаголы, короткие причины. Сообщение строится как «что произошло → что можно сделать». Technical details раскрываются отдельно.

| Случай | Предпочтительный текст |
|---|---|
| Неясный исход | `The result is not confirmed. Check the original command before sending again.` |
| Revision conflict | `Settings changed elsewhere. Your edits are still here.` |
| Provider hold | `This provider is temporarily unavailable. You can keep reading or choose an available model.` с реальной причиной ниже. |
| Interrupt fallback | `The turn did not confirm interruption. Swarm stopped the agent.` |
| Частичный diff | `Some changes are omitted by the preview limit.` |
| Недостаточно данных | `Not reported by this harness.` либо `Last read …`, по фактической причине. |
| Пустой список | `No tasks in this project yet.` + New task, если действие допустимо. |
| Ошибка формы | `Choose a workspace before starting.` рядом с полем. |

Текст `Success` не заменяет содержательный результат. Для собственного UI не употреблять противоречивые синонимы одной операции: Stop turn, Stop Agent и Stop Swarm всегда различимы.

## 20. Данные, скорость и устойчивость

### 20.1. Разделение ответственности

| Слой | Отвечает за | Не делает |
|---|---|---|
| Daemon / Store / native adapters | Work state, admission, routing, commands, events, durable outcome, settings и policy | Не отдаёт владельцу догадки UI как истину. |
| Typed desktop client | Bounded RPC, subscriptions/cursors, canonical DTO, cancellation/readback | Не создаёт альтернативный protocol через произвольный JSON. |
| UI state | Selected route, draft, expanded rows, local selection, scroll anchor | Не дублирует durable task engine, quota engine и command replay queue. |
| WinUI rendering | Layout, text, input, native control states, bounded обновление видимого содержимого | Не выполняет Git/RPC/disk walk на UI thread. |

Native auth flow — уже предусмотренное узкое исключение для интерактивного входа; оно не даёт UI право выполнять обычную агентскую работу вне daemon. Текущий desktop связывается с Windows daemon через named pipes; Linux-сборка или mock transport не доказывают desktop runtime. [R2]

### 20.2. Что защищает отзывчивость

- RPC, filesystem, Git, большие parsing/diff операции выполняются вне UI thread. Из background возвращается bounded результат; изменение WinUI objects происходит на UI dispatcher. [W17]
- События сохраняют причинный порядок, но промежуточные визуальные snapshots можно объединять. Финальный ответ, blocking request и error не теряются при coalescing.
- Render cache зависит от ревизии конкретного блока. Keystroke в composer не пересоздаёт sidebar, все turns, menus и theme resources.
- Collapsed work logs не создают полный набор невидимых child controls. Закрытая pane не читает diff/process/resources по таймеру.
- Git/disk-heavy сведения загружаются при открытии/Refresh. Sidebar работает на bounded projections; catalogue использует существующий watch. Нельзя каждую секунду перечитывать весь `daemon.status`, каждый project и каждый worktree.
- State обновляется по Agent/generation/turn/request/revision, а не по текущему выбранному экрану. Late responses старого route/session не меняют новый.
- Loading indicator локален к занятой области. Ошибка одной строки не убирает весь экран под глобальный spinner.
- Minimized/hidden окно не крутит декоративные animation loops. Background subscriptions не теряют работу, но визуальные ticks, expensive projections и анимации сокращаются.

Нужны обе границы: количество данных в cache и количество UI elements в viewport. Наличие ItemsRepeater само по себе не доказывает virtualization: конечный viewport, layout и data source должны быть совместимы. Текущий rich transcript использует bounded keyed StackPanel после проблемы realization/anchoring. Для fleet/history выбирать работающую bounded реализацию по профилю. [C3], [C4], [Q1], [W18], [W19]

### 20.3. Бюджеты — цели Swarm, ещё не измеренные результаты

Референс для приёмки: Windows 11 x64, SSD, 16 GiB RAM, обычная integrated GPU; в отчёте фиксируются точные CPU/Windows/runtime/build, размер реальных данных и DPI. Release build, одинаковые условия до/после. Платный inference не нужен для проверки темы, навигации и исторического transcript.

| Проверка | Цель |
|---|---|
| Набор текста / обычный selection | P95 input-to-visible response ≤50 ms; отсутствие зависаний UI thread ≥100 ms в типовом взаимодействии. |
| Переход в уже загруженную задачу/Settings | P95 до полезного содержимого ≤150 ms. |
| Cold/warm startup | Измерить отдельно; видимая оболочка не ждёт полного catalogue/history/fleet. Зафиксировать baseline и устранить регрессию, вместо выдуманной универсальной цифры. |
| Streaming | Набор текста, меню и чтение истории остаются отзывчивыми; нет повторного layout всей истории на каждый chunk. |
| Long transcript | Реальная история у текущего resident limit; Load older, collapse и Jump to latest не оставляют пустые unrealized участки. |
| Repeated navigation | После прогрева и 20 циклов открыть/закрыть те же задачи/panes память выходит на плато в пределах bounded caches; нет роста числа handlers/subscriptions. |
| Idle/minimized | Нет постоянной загрузки ядра из-за UI polling/animation; источник заметного CPU wakeup измерен и объяснён. |

Эти цели проверяются на текущем Windows стенде и настоящих данных. Изменение темы не даёт оснований обещать конкретный размер EXE, RAM или FPS без измерения. Не создавать отдельную performance platform, benchmark suite или fake harness ради отчёта. Использовать существующие project gates и доступные Windows profiling tools для конкретной проблемы. [R3], [W26]

### 20.4. Устойчивость состояния

| Риск | Обязательное поведение |
|---|---|
| Double click / повторный Enter | Один pending action; повтор не создаёт новую mutation. |
| Timeout после admission | Readback исходного ID; Unknown отделён от отказа. |
| Смена route во время запроса | Результат записан своему scope; новый экран не перехвачен. |
| Обновление generation | Старые controls/response не действуют на новую generation. |
| Concurrent config edit | Revision conflict, draft сохранён. |
| Event gap | Resnapshot/cursor recovery, сохранён пользовательский контекст. |
| Theme change | Draft, focus, selection, scroll и pending operation сохранены. |
| Missing/corrupt data | Локальная ошибка с причиной; нет panic и пустого окна без recovery. |
| Отмена чтения | Завершается UI interest; уже admitted durable mutation не объявляется отменённой только из-за закрытия pane. |

### 20.5. Что хранить

Текущий `[desktop].window` уже сохраняет размер/позицию/maximized state. Соблюдать единицы и clamp действующего API: XAML layout values, DPI и physical screen coordinates не смешиваются. Не переписывать window settings на каждый render.

Display names, favorites/recent и имеющиеся preferences использовать из текущего config. Новые sidebar/pane/work-log preferences пока могут быть session state; для сохранения между запусками нужны явные bounded typed поля в том же config и revision-safe save. Draft persistence на диск — отдельное продуктовое решение: обязательна сохранность при навигации в текущем процессе, но не следует обещать восстановление после crash без реализованного хранения.

## 22. Rust, Reactor и миграция Material

### 22.1. Зафиксированный технологический выбор

**Остаёмся на Rust + WinUI 3 + Microsoft windows-reactor.** WinUI уже предоставляет Fluent controls. Смена визуального языка не требует переносить daemon, переписывать приложение на C# или внедрять иной renderer.

Desktop использует upstream windows-rs через git source; `Cargo.lock` фиксирует разрешённый commit. Ветка приложения уже использует API из актуального source graph для scoped monospace в `TextBlock` и нативных ScrollView metrics/requests. Это подтверждение реализации по исходникам, не Windows runtime-приёмка. Reactor остаётся preview; его опубликованная версия и upstream source version — разные сведения. [C1], [Q2], [Q3], [Q6]

Версии `0.100.0` и связанная с ней release guidance ниже сохранены как исторические ссылки для прежнего crates.io snapshot и runtime-контракта. Они не описывают текущую dependency base. Текущие несовершенные места определяются кодом и проверяются на Windows; не возвращать ограничения старого API как незавершённые задачи.

### 22.2. Матрица совместимости

| Область | Исторический crates.io snapshot 0.100 | Текущее приложение / API | Решение |
|---|---|---|---|
| Stock Fluent controls | Доступны | Текущий UI использует штатные controls | Не переписывать templates. |
| `ItemsRepeater` / `VirtualSource` | Доступны | Rich transcript использует bounded keyed `StackPanel` после проблем realization/anchoring | Не объявлять virtualization готовой по факту наличия API; выбирать по профилю. |
| Code-only `font_family` | В crates.io 0.100 отсутствовал | `TextBlock::font_family` уже применяется в code preview | Scoped monospace; не менять глобальный font key. |
| Editable code font | В crates.io 0.100 отсутствовал | У `TextBox` builder по-прежнему нет этого свойства | Небольшие editable поля оставлять со штатным шрифтом; code preview/Open in editor — отдельная граница. |
| Scroll metrics / programmatic scroll | В crates.io 0.100 отсутствовал | Используются `observe_view`, `ScrollViewMetrics`, `request_scroll_to` | Сохранять follow/jump и позицию чтения; проверить на Windows. |
| Key/focus callbacks | Ограниченная поверхность | Hooks остаются для конкретных случаев | Проверять keyboard/IME/focus на Windows; наличие callback не доказывает все сценарии. |
| Native menu callbacks | Старая реализация сопоставляла labels | Текущий WinUI flyout bridge сохраняет item/action mapping | Не dispatch-ить по локализованному отображаемому тексту; проверить lifecycle/focus. |
| Flyout imperative lifecycle | Не вся поверхность доступна через Reactor | Swarm сохраняет необходимый WinUI bridge | Это native interop, не повод заменять меню самодельными controls. |
| Theme brush inventory | Небольшой enum | По-прежнему ограниченный набор | Использовать native control states; не вводить palette engine. |

Direct dependencies на `windows-core`, `windows-reference`, `windows-collections` и transitive crates должны соответствовать upstream workspace graph: `collections/core/future/reference/time/window` — 0.101.0, `windows-threading` — 0.100.1; optional `windows-reactor-setup` — 0.100.1. Не смешивать несовместимые WinRT types из двух версий и не назначать всем пакетам номер 0.101 по догадке. Track upstream windows-rs; `Cargo.lock` records the resolved commit; resolution/fetch проверяются и на Linux CI, поскольку target-specific dependencies участвуют в графе Cargo. [Q2], [Q3], [Q9]

### 22.3. Runtime и поставка

Release guidance для Reactor 0.100 и упомянутая там Windows App SDK 2.4.0 относятся к историческому опубликованному snapshot. Swarm не подключает `windows-reactor-setup` и использует установленный Windows App Runtime. Runtime фактически установленной Windows следует фиксировать в runtime evidence; source setup package version сама по себе не задаёт deployment contract. Bootstrap и поддерживаемую deployment model подтверждать на Windows; self-contained поставка не следует из перехода на Fluent. [C1], [Q4], [Q5], [Q6]

WinUI Gallery snapshot использует `2.6.6-experimental` в `standalone.props`. Gallery — образец поведения и композиции, его dependency file нельзя копировать в Rust production app. Переход на Fluent сам по себе не требует менять packaging на self-contained. Проверить установленный runtime и запуск на чистой поддерживаемой Windows в принятой deployment model. [G3], [W21]

### 22.4. Текущая база и оставшиеся UI gaps

Текущий Fluent desktop уже использует `TextBlock::font_family`, ScrollView metrics/requests и native Flyout/MenuFlyout bridge в `views.rs`, `flyout.rs` и `menu_ui.rs`; предмет оставшейся проверки — реальные Windows focus, scroll, accessibility и deployment scenarios. §21 остаётся единственной картой продуктовых UI gaps: различать готовый backend contract и отсутствующий desktop caller, например для task/checkpoint reads и `agent.diff`. Не создавать задачи на миграцию отсутствующих Material modules/resources и не объявлять roadmap Goal increment A12 реализованным по наличию Goal UI. [C29], [C35], [C39]

### 22.5. Legacy theme values

Старые значения configuration должны читаться без поломки запуска. Принятое отображение: System→System, Light→Light, Dark→Dark; Purple→Light, Amoled/Neon/Matrix→Dark по прежнему light/dark характеру. Legacy значения не показывать как действующие дополнительные темы. Нормализация выполняется контролируемо через existing configuration flow, без записи при каждом render и без потери concurrent revision. [C40], [R4]

### 22.6. Заморозка Material

Сохранить доступный Git commit/историю предыдущей реализации и пометить направление как frozen в существующем roadmap. Не вести рядом второй renderer, набор feature flags, theme dictionaries или двойной визуальный regression suite.

Возврат возможен отдельным будущим решением, когда выбранные native APIs позволяют полноценно оформить необходимые controls, states, typography, scrolling, accessibility и motion без глобальных опасных подмен. До этого любые улучшения делают Fluent-клиент лучше; они не обязаны готовить скрытую Material-совместимость.

## 23. Приёмка

Порядок реализации и статус принадлежат [roadmap](../roadmap.md). Этот документ задаёт требования к дизайну и приёмке, а не параллельный этапный план. Windows review должна охватить Home, длинную беседу, blocking decision, Changes, Project и Settings; фиксировать только реально наблюдённые результаты. Gallery служит источником поведения controls, не заменой проверки приложения.

### 23.1. Чек-лист сдачи

| Область | Доказательство готовности |
|---|---|
| Дизайн | Никаких Material fonts/palette/templates в действующем UI; единая typography/spacing; primary action и иерархия читаются. |
| Основные сценарии | Сквозные пути §18.2 пройдены на реальном daemon в пределах разрешённых окружением действий; результат зафиксирован. |
| Все состояния | Empty/loading/partial/stale/error/unknown/permission refusal отображены там, где применимы; не только happy path. |
| Keyboard | Каждый частый action доступен без мыши; корректны Tab/arrows/Enter/Esc/context menu, возврат focus и IME. |
| Accessibility | Readable Light/Dark/Contrast, доступные names, текст до 225%, visible focus, нецветовые status/diff markers. |
| Layout | 640×480, 900-wide, 1280×800, широкое окно; нет перекрытого composer, скрытых dialog buttons и недостижимых actions. |
| Data correctness | Никакого auto-replay unknown mutation; точные generation/request bindings; config conflict сохраняет draft. |
| Performance | Release measurements по §20; long transcript и repeated navigation без concrete regressions. |
| Deployment | Задокументированный runtime, нормальный запуск/закрытие, clean-machine check принятой модели установки. |
| Source hygiene | Неиспользуемые M3 assets/deps удалены, source pins/license notes корректны, roadmap и owning specs отражают изменения. |

Build gates брать из актуального `AGENTS.md`: scoped `cargo fmt --check`, locked build и применимый clippy с предупреждениями как ошибками. Не возвращать удалённый test suite, не строить fake harness и не добавлять новый общий verification framework. Успешная сборка подтверждает типы/линковку, а не scrolling, focus, glyphs или удобство. [R3]

### 23.2. Когда остановить неправильную реализацию

Вернуть изменение на исправление, если оно:

- меняет глобальный font/resource key ради одного code block;
- подменяет native Button/Menu/Dialog нарисованным набором Border/TextBlock без поведения;
- делает новую тему, но оставляет M3 overrides активными;
- пересобирает окно/историю при каждом keystroke или event;
- выводит presumed progress/empty/Ready вместо unknown/partial/stale;
- выполняет Git/RPC/large parse на UI thread;
- повторяет uncertain mutation новым ID;
- изображает несуществующий API или неработающий control как готовую функцию;
- теряет focus, draft, selection либо scroll при обычной навигации/теме;
- объявляет дизайн «идеально отлаженным» только по screenshot или cargo build.

Цель документа — снять неоднозначность задания и обеспечить проверяемую поставку. Полное отсутствие дефектов нельзя подтвердить исследованием исходников; готовность означает, что перечисленные сценарии и ограничения действительно проверены в принятой Windows сборке.

### 24.6. Критерий использования источников

Перед добавлением каждого нового видимого действия исполнитель должен знать: native control, место на экране, state/empty/error вариант, точный backend owner и допустимый результат. Если эти пять вещей определены в этом документе и owning spec, следующий шаг — реализация и проверка, а не новое исследование всех UI frameworks.

Ни один источник здесь не доказывает, что текущий Swarm уже прошёл Windows-приёмку Fluent. Комплект даёт согласованный дизайн, точные зависимости и проверяемый маршрут к готовому приложению.
