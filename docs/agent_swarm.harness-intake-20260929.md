# Harness rev5 → ELIOT Swarm: отбор полезных выводов

**29.09.2026. Дополнение к архитектуре v16, не новая архитектура и не самостоятельный upstream-аудит.**

Источник **H**: [Harness and OpenCode Go master, rev5](Harness_and_OpenCode_Go_master_2026-09-29_rev5.md), предоставленный пользователем. Ниже «описано/подтверждено» относится к этому исследованию. Его CODE/DOC/ISSUE/INFERENCE сохранены как авторские уровни evidence; в этом проходе исходники кандидатов, лицензии и установленные binary независимо не проверялись.

Действуют [архитектура v16](agent_swarm.md) и [план v4](agent_swarm.implementation-v4.md). Пины доноров, SQL, семь выбранных runtime-модулей и порядок C01–C11 не изменены. Новые продукты не устанавливались.

## 1. Разные задачи — разные критерии отбора

H выбирает самостоятельный менеджер/harness с Goal, GUI, телефоном и доступом к Go/Muse. Наш прототип — headless-контроллер разных родных harness, которым управляет General Manager. Поэтому рейтинг H не является рейтингом готовых замен нашего сервиса.

| Положение H | Применение к прототипу |
|---|---|
| Предпочтение standalone GUI/телефона | Не входит в текущий объём. Закрытие любого внешнего UI не должно выключать нашу очередь и доставку. |
| Codex + OpenCodex — основной Go/Muse-маршрут для задачи H | Не назначает Codex обязательным GM и не заменяет отдельную подписочную Muse Code Max. |
| Один writer и read-only helpers в общем checkout | Частный режим совместной записи. Не превращать в ограничение одного исполнителя на весь многолинейный controller; правила конфликтующей записи и main-only остаются действующими. |
| Наличие sandbox и ограничителей повышает рейтинг harness | Полные разрешения прототипа не пересматриваются. Управление заданиями и проверяемая приёмка не равны физической изоляции недоверенного агента. |
| Настоящий Goal должен иметь пределы run | Сохранять сведения о native-пределах. Не вводить самостоятельно новый глобальный timebox/25-turn cap для наших Issue. |

Открытый исходник и маленький binary ещё не доказывают простоту выделения библиотеки. Новый model loop не переносится в ELIOT только ради одного полезного таймера.

## 2. Что действительно полезно

### Goal — не один boolean

H §4.3 описывает у Graff сохранённую objective/checklist, но run-local credits/deadline и отсутствие автоматического crash-resume. H §5.2 показывает другой разрыв: Sinew хранит Goal в SQLite, а следующий ход запускает React-effect. H §9.1 описывает у Kilo переход активной Goal в paused после restart.

**Следствие для интеграции:** отдельно выяснять сохранность цели, владельца продолжения, наличие фоновой работы и поведение после restart. Всё это помещается в существующий capability report/native state адаптера, без новой таблицы или общего Goal-engine.

Сохранённая цель не означает продолжающееся исполнение; paused после восстановления не означает failed; native run limit не означает принятую Task. При активном native goal контроллер не запускает второй цикл «продолжай».

### Ожидание работы — не потеря работоспособности

В H §4.2 Graff переходит в holding при background shell/subagent и просыпается по завершению. Полезен принцип, не конкретный 25-turn guard.

У нас known waiting с наблюдаемым child/check отличается от неизвестного состояния. При наличии готовой независимой работы можно направить содержательный nudge менеджеру; пустой polling модели ради запрета idle не нужен. Если завершение перестало наблюдаться, сначала сверяется executor, а не перезапускается агент.

### Таймер и доставка — разные операции

H §9.2 описывает native wakeup/cron Kilo, восстановление после старта и отсутствие массового воспроизведения пропущенных recurring slots. H §4.4 отдельно отмечает: сохранённый Graff one-shot не запускает выключенный Windows-процесс.

**Для текущего scheduler:** использовать существующие due Operations и native callbacks. Запись очередного срока до отправки предотвращает некоторые дубли, но сама по себе не гарантирует доставку: crash между записью и отправкой может потерять wakeup. В прототипе нужны уже выбранные durable Operation и reconciliation, а не новая независимая очередь.

При due-time проверять актуальные Task/binding/continuation revision и disposition. После Pause/Clear/supersede старое пробуждение не должно включать работу заново. Reconnect не должен стирать уже принятый ответ. Пропущенные слоты объединять по политике задания, не создавать шторм prompts. При неизвестном native admission не повторять вслепую.

### Два протокольных слоя нельзя смешивать

H §4.7, §6 и §9.7 различает Responses, Chat Completions и Messages на уровне provider/model. H §9.7 также описывает Go session identity не только на основном inference, но и на служебных путях.

```text
MCP / наш IPC → управление работой
HTTP / MSP / ACP / app-server → управление native harness
Responses / Messages / Chat Completions → inference внутри harness/provider
```

Контроллер нормализует первые два уровня, но не становится новым inference proxy. При подключении маршрута надо подтвердить именно нужную модель, tools, детей и используемые вспомогательные вызовы. Работа обычного чата не доказывает исправность compaction, titles или memory calls.

`x-opencode-session` проверяется в native/provider-интеграции, когда того требует конкретный маршрут. Не добавлять его ко всем запросам нашего IPC и не выдумывать одну общую session identity для всех агентов. Правильное отношение root/child идентификаторов задаёт provider-контракт, а не совпадение названий Task и lane.

### Board post не является wakeup или assignment

H §9.5 прямо отделяет Kilo Swarm board от запуска, назначения и остановки агента. Это подтверждает полезность нашего разделения: mailbox admission, native delivery, реакция получателя и смена владельца Task — разные факты.

Общение между менеджерами оставляем свободным и адресным. GM не пересылает каждую реплику. Новые семантические подписки или отдельный chat-server для этого не нужны.

### Checklist gate не заменяет приёмку

H §2.5 и §4.2 различает self-report, controller completion gate и независимую проверку. Даже два вызова complete после checklist не делают проверку независимой, если их содержание контролирует implementer.

Сохраняем существующую связку candidate + требование + CheckRun + решение приёмки. Новое ручное разрешение для каждого инструмента не требуется. При полном доступе агентов нельзя называть внешний verifier физически защищённым без отдельной изоляции; прототип обеспечивает отдельного владельца приёмки, а не вымышленную песочницу.

## 3. Новые кандидаты: что изучать, не что устанавливать

| Кандидат из H | Полезная область | Текущая диспозиция |
|---|---|---|
| Kilo CLI | Native waiting/wakeup/cron, descendant cancellation, protocol-per-model | Приоритетный источник сравнения для scheduler и optional runtime. Не зависимость C01–C06, не замена Muse Max. |
| CodeGraff + Harness | Разделение objective/run, holding/wake, headless control, child jobs | Источник идей и возможный поздний executor. H сообщает Chat-Completions-only router и modified AGPL: перенос кода требует отдельной проверки точной лицензии/замыкания. Не разрешать его архитектуре навязать свой model loop или 25-turn cap. |
| Pi-Go | Process subagents, single/parallel/chain, выбор inference-протокола на уровне модели | Возможный optional worker. По H каталог не содержит требуемый Muse и отсутствует persistent Goal; не приписывать совместимость официального Pi. |
| Sinew | Peer tasks/messages, пример UI-owned continuation | Источник для анализа coordination, не always-on runtime по H. GUI не переносить. |
| OpenChamber | Отрицательные примеры stale continuation/lost wakeup/restart scan | Регрессионные ситуации для наших Operation/revision/reconciliation. Закрытый issue не означает слитый fix. |
| Tatsu Code | Сравнение поведения интерактивного исполнителя | По H закрытый продукт; донор исходников не установлен. Не включать в build. |

Ни один кандидат не добавлен в исполняемый donor inventory или матрицу квалифицированных маршрутов. Штатные доноры остаются прежними. Если позднее выбирается новый донор, берётся целая пригодная единица с dependency closure и notices, а не переписанная по H псевдореализация.

## 4. Привязка к существующему плану

| Пакет | Что учитывать при реализации/квалификации | Чего не добавлять |
|---|---|---|
| C03 / C07 | Native Goal persistence, restart disposition, request admission, независимый task acceptance | Второй общий Goal engine, автоматический обход vendor budgets |
| C04 и любой Go-маршрут | Root/child и реально используемые служебные inference paths, billing/model/effort binding | Собственный Responses/Chat/Message gateway |
| C05 | Due wakeup с текущей revision; mailbox ≠ delivery; coalescing missed slots | LLM-heartbeat, массовый catch-up prompts, чат-модератор |
| C09 | Известное waiting отдельно от fault, независимое решение по candidate | Kill по idle, ложная защищённость full-access проверки |
| C10 / C11 | Поведение resume/update оценивается для actual entrypoint | Автоматический перенос verdict между версиями/GUI/CLI |

Это уточнения для уже выбранных участков, а не новые prerequisites C01. Сначала остаются model/config/store и host/CLI/IPC, затем Muse и OpenCode. Не начинать новый конкурс платформ только из-за расширившегося списка названий.
