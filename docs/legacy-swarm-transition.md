# Legacy Swarm transition

The legacy Swarm skill supplied routing guidance, launch templates, scripts, and evidence habits. ELIOT already owns task admission, native sessions, operations, checks, reports, and acceptance. Carry useful controls through those owners; do not introduce a second scheduler, session owner, run database, or completion authority. This document describes mechanisms and gaps, not live qualification of a provider or installed launcher.

## Host-specific skill migration boundary

The retired host-specific skill is migration evidence, not an execution or authority surface. Do not carry its provider/model defaults, fixed manager or conversation/session bindings, direct host start/stop scripts, heuristic retries/timeouts, or usage-as-quota rules into current controller behavior. Any native session identity that a supported adapter still needs belongs only to the current authenticated binding and its exact durable Operation/readback contract; a legacy manager handle does not establish ownership.

The launcher assignment context defines swarm.launch.preview as an effect-free plan and swarm.launch as the manager/current-owner admission operation using the exact preview digest and a caller-owned request ID. It revalidates current Task/Attempt/dependency/workspace facts, records intent before external effects, delegates work to existing owners, and reconciles uncertain effects by exact readback. That document explicitly marks its methods as design targets until implemented and qualified; method names or a historical successful input do not establish a live endpoint or accepted Task.

Carry forward only host-independent collaboration controls that fit current owners: explicit objective/scope/stop conditions, one manager for fan-out, exclusive writer scope, independent verification, and evidence tied to exact durable Operations/source revisions. Keep Task, Attempt, Operation, artifact, check, and acceptance records as the existing sources of truth; do not restore a parallel skill run database, session scheduler, provider quota ledger, or completion authority.

## Mechanism mapping

| Legacy control | Current owner | Coverage and boundary |
|---|---|---|
| Launch brief, task receipt, and run identity | [`TaskSpec`](../src/model.rs), Task/Attempt/Operation, caller request receipts, and [`RuntimeCommand`](../src/runtime/mod.rs) | TaskSpec records objective, phase, requirements, dependencies, scope, source references, and optional acceptance. Route is chosen at `agent.open`; runtime commands bind an operation to a binding generation and native root. There is no first-class run-record API, and TaskSpec has no typed model, variant, effort, budget, or stop-condition fields. Keep those as explicit caller/manager instructions and report the gap; do not imply they are durable Task fields. |
| Continue the exact native session | Binding generation, native root/session identity, [`operation.get`](../src/mcp.rs), `agent.reconcile`, and `agent.recover` | The OpenCode V2 adapter addresses an existing session and reconciles uncertain effects by readback. A lost response is not permission to resend: reconcile the original operation and keep `Unknown` if native evidence is missing. Session-continuation details remain adapter-specific; there is no generic CLI `--continue` contract. |
| Current route/model catalog and canary | [`route.list`](../src/store/mod.rs) and adapter-native catalogs/readback | `route.list` reports configuration only and explicitly is not live qualification. OpenCode V2 validates exact catalog IDs, variants, and catalog revision when configuring/reading a session. There is no universal canary operation. A canary must be explicitly authorized, bounded, and scoped to the exact route; its result proves only that observed execution, not future availability, cost, quota, or another route. |
| Logs and stream/NDJSON receipts | Operation outcomes plus immutable [`artifacts`](../src/artifacts.rs) and bounded `artifact.read` pages | Artifact metadata and pages preserve bytes and hashes. The controller has no general Claude/OpenCode CLI `stream-json` ingestion contract. Do not treat arbitrary stdout, a parsed partial stream, process exit, or a quiet session as completion. If an adapter lacks a terminal receipt, preserve the operation as `Unknown`/incomplete. A future stream adapter must correlate exact operation/session IDs, keep stdout and stderr distinct, and define truncated, malformed, and missing-terminal behavior before it can claim completion. |
| Independent alarms and monitoring | `report.delta`, `report.attention`, `report.capacity`, `host.status`, and native adapter readback | Reports are controller projections of committed facts. Confirm an actionable alert against the exact operation/binding and native source before acting. `doctor.inspect` is read-only diagnostics; it does not independently poll a provider, restart a worker, or kill a process. Controller capacity reports are not provider quota evidence. |
| Independent verification and acceptance | [`CheckRunner`](check-runner.md), Task submission, review, and `task.accept` | Capture one exact source revision, run only a configured check profile, retain its receipts, and use a separate reviewer/acceptance owner. A writer’s summary, launcher exit code, or provider response is not acceptance. |

The run brief should assign exclusive path ownership and a distinct verifier while respecting the repository’s current owner policy. Preserve the Claude variant’s useful flat-orchestration control: the selected manager owns native fan-out and integration; workers do not create competing manager trees. Legacy worktree-per-writer behavior, provider/model defaults, heuristic timeout kills or retries, and aggregate usage-as-quota rules are retired; they must not override the current owner or route policy.

## Operator runbook

1. Start only on an explicit user/operator request. Record the objective, non-goals, requirements, source revision, allowed paths, acceptance evidence, stop conditions, and the exact authorized route/model/variant where that route exposes them. Use a stable caller-owned request ID for each mutation.
2. Read the current configured route and the selected adapter’s live catalog. If the exact agent, model, or variant is absent, stop with that evidence. Do not silently select a different provider or model. Perform a bounded canary only when explicitly authorized; record it as route-specific evidence, not as quota or general qualification.
3. Before claiming, select the applicable [Owner Policy edition](task-policy.md) and canonical source set: the exact Issue revision, source comments selected into it, and canonical documents. A generated Task/brief is a projection; preserve unresolved source comments as gaps. New Attempts freeze the accepted policy identity and ordered source index. A selected source entry requires its exact revision, text and SHA-256; legacy references remain explicit gaps rather than becoming pinned sources. Create/claim the Task and Attempt through the existing owner, then bind the producer to the exact native session and issue each intended mutation once. Keep Task revision, Attempt, submission/candidate reference and digest where supported, operation IDs, binding ID/generation, native root/session IDs and readbacks together. A raw TaskSpec does not prove that the operator selected a complete canonical source set.
4. Follow the exact Operation and committed reports. On a lost response or uncertain native effect, call the adapter’s addressed reconciliation/readback path for the original operation. Do not replay a mutation or open a replacement session to guess the outcome. Keep unresolved evidence `Unknown`.
5. Publish result/log material only through the existing immutable artifact/result flow supported by that adapter. Record byte length and digest; avoid raw secrets in task text or public reports. If the adapter cannot produce a terminal receipt, report incomplete rather than success.
6. Capture the exact candidate and use the existing `source.capture → task.submit → check.run → task.accept` path where acceptance requires checks. Review the result independently against the captured source and configured profile.
   Before relying on symbol or caller-impact queries, verify the graph's index status and source revision. An unavailable, empty or stale index is an evidence gap; a graph miss does not prove no impact. Record post-edit changed-symbol impact evidence alongside the diff and check receipts.
7. Before closing, reconcile actionable alerts against their owning Operation or native session. `Unknown` blocks a new mutation or replay, but already-authorized exact readback/reconciliation may continue. Preserve unresolved evidence; request a new explicit decision only before changing route/scope outside the existing authorization or admitting a new effect while the prior outcome remains unknown.

## Known integration gaps

- No durable first-class Swarm Run/launch-manifest API carries route, model, variant, effort, budget, and stop conditions alongside Task/Attempt/Operation.
- Policy/source-index binding is implemented for new Attempts, while selection of complete canonical evidence remains the operator's responsibility; generated task text cannot replace or hide that set.
- Native terminal ingestion remains adapter-specific. The Command sessionless bridge and Zed batch host now correlate saved operation/run/result evidence; there is no universal arbitrary-CLI stream parser.
- No universal provider canary API or cross-provider live-qualification record exists; configured routes and catalog presence are not execution receipts.
- Exact continuation and reconciliation are adapter-specific. Do not promise continuation for an adapter until its native identity and readback contract are implemented and qualified.

Until those gaps are closed, preserve them in the manager’s explicit brief and final report. Do not create parallel scripts or stores that compete with controller operations, artifacts, checks, or acceptance.
