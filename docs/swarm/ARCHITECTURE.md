# Swarm: суть и правила

> Короткая версия целевой архитектуры v2.6 (27.11.2026). Читай первым при любой задаче. Подробности — [implementation/](INDEX.md#файлы), связи — [GRAPH.md](GRAPH.md), что проверено — [STATUS.md](STATUS.md), полный текст правил — [decisions.md](implementation/decisions.md).

## Что это

Swarm — оркестратор харнессов (Claude Code, Codex, OpenCode, ACP-харнессы и облачные агенты). Это конвейер производства, а не память: у каждого участника роль и рабочее место, работа течёт по этапам, участник, который не справляется, заменяется, а работа остаётся на месте. Memory OS — отдельный проект; от неё остаётся только Memory API (D-38) как внешний сервис.

**Цель.** Задача крутится в цикле, пока не будет действительно готова и влита в main. Агенты продолжают работать при сбоях провайдера, харнесса или демона; система помогает и переназначает работу; повторное ложное «готово» или застревание отдаётся на разбор другой модели. Merge, squash, чистка — автоматически; владелец может включить ручное подтверждение любого перехода.

**Ядро.** Передача сообщений по образцу Erlang/OTP на Rust и tokio: акторы, супервизия, let it crash, большой поток транзакций.

## Роли

- **Менеджер** (агент): режет цель на задачи с проверяемыми критериями и областью записи.
- **Исполнитель** (агент): одна задача в своём worktree.
- **Ревьюер** (агент другой модели): проверяет дифф по критериям задачи, а не рассуждения исполнителя.
- **Разборщик** (агент другой модели или семьи): разбирает застрявшую задачу и решает, что дальше. Ревью проверяет дифф, разбор — застрявшую задачу.
- **Интегратор** (код демона, не LLM): очередь merge, squash, push, чистка. Единственный, кто меняет main.
- **Супервизоры** (код): следят за процессами и перезапускают их.
- **Владелец** (человек): ставит цели; в ручном режиме подтверждает переходы с gate = owner.

## Двенадцать правил (сжато)

1. Правда о задаче одна: транзакция в Store (SQLite демона, synchronous=FULL). Переход принят, когда записан. work-truth.git — определения и история, остальное — кэш.
2. Участники общаются только сообщениями; общей изменяемой памяти нет.
3. Сбой не чинят на месте: перезапуск с известного состояния.
4. Падение одного агента, харнесса, демона или записи очереди не останавливает остальных.
5. Агенты игнорируют инструкции. Всё важное проверяет код в момент действия.
6. Контроль не на пути потока: Stop hook держит ход не больше 3 раз подряд без прогресса; по умолчанию владельца ждёт только deploy.
7. «Неизвестно» ≠ «провал»: сначала читаем источник, неясное — на разбор, а не на слепой повтор.
8. Задача живёт вне агента и харнесса; любой агент подхватывает её в любой момент.
9. Один реестр команд, один конверт сообщения, один формат задачи.
10. Секрет в одном месте: агент не держит ни ключа провайдера, ни токена forge; код агента не исполняется в процессе с токеном. Два названных исключения не расширяются.
11. В первую волну — только то, без чего задача не переживает сбой, или чей эффект измерен. Без криптографии и церемоний: id сообщения, номер поколения и SHA коммита достаточно.
12. Параллелизм ограничен пропускной способностью интегратора и проверок; метрики считают принятый результат и полную цену.

## Модель: 16 сущностей, у каждой один писатель

**Task** (задача, id + rev): ready → claimed → running → checking → review → queued → integrating → done; плюс held(причина) и cancelled. **Attempt** — исполнение задачи ролью (executor, reviewer, analyst, manager); номер Attempt исполнителя и есть поколение gen. **Runtime** — процесс харнесса одного Attempt (или удалённая сессия, kind = remote). **Envelope** — конверт сообщения; **Delivery** — его доставка агенту; **Event** — журнал фактов. **Candidate** — результат как OID коммита на (rev, gen); **CheckRun** — прогон проверки для дерева; **Verdict** — решение ревью или разбора; **Gate** — ожидание решения (владельца или автоматического); **Stop** — причина остановки; **IntegrationStep** — шаг интегратора с журналом; **Workspace** — worktree, ветки, карантин; **Hold** — запрет маршрута (квота, авторизация); **Grant** — права удалённого принципала; **Note** — заметка агента. Кто что пишет — [GRAPH.md](GRAPH.md#кто-что-пишет).

## Как течёт работа

`Task.gen` — номер executor Attempt; локальный `Agent.generation` — поколение нативного запуска. Это разные счётчики: resume сохраняет Attempt и `Task.gen`, но создаёт новый Runtime с новой привязкой `agent_id + agent_generation`. Полномочия и события проверяются через эту привязку, а не равенством двух чисел. Подробности — [automata.md](implementation/automata.md#жизненные-циклы-остальных-сущностей).

Менеджер создаёт Task → планировщик выбирает route (харнесс, модель, аккаунт) → одна транзакция захвата создаёт Attempt и команду запуска → runtime агента (отдельный процесс, переживает рестарт демона) ведёт харнесс → агент коммитит в свою ветку и говорит `swarm done` → демон сам запускает проверки → ревьюер другой модели → Candidate в очередь → интегратор пересобирает на свежий main, проверяет, push fast-forward → done, когда OID кандидата достижим из origin/main. Сбой процесса — resume того же исполнения; ложное «готово», тишина, отказы ревью — детектор, held(analysis), разбор и, по вердикту, новый исполнитель (gen+1) с пакетом передачи.

## Технология и границы

- Rust, tokio; крейты eliot-core (типы и reducer без IO) → eliot-store (единственный rusqlite) → eliot-daemon; eliot-plugin и плагины-процессы по NDJSON; eliot-client — единственный путь CLI, MCP и desktop в демон.
- CLI-маршрутизатор `swarm` по одному реестру METHODS; MCP из двух инструментов (swarm_search, swarm_run).
- Hooks и injects доставляют сообщения в ход, но барьер — это действие кода (interrupt, новое поколение, отказ интегратора), а не текст.
- GitHub и другие forge нужны только интегратору; задача стартует и работает без них.
- Не делаем: свой компактор, «ровно один раз», произвольный движок workflow, шифрование ради церемонии.

## Доказано и гипотеза

В v2.6 сообщены результаты прототипов: SQLite-очередь 1 тыс. сообщ./с, p99 17 мс, 0 потерь после kill -9; хуки Claude Code 2.1.332; журнал интегратора с чтением origin. Исходные артефакты этих прогонов в данном checkout отсутствуют; это не замер текущего продукта. Гипотезы: другие харнессы (только исходники), облачные агенты и удалённый MCP, Windows, сбой питания, пороги детектора. Перед опорой на механизм смотри [STATUS.md](STATUS.md).
