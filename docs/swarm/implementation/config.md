# Конфигурация конвейера: workflow.toml, routes.toml, triggers.toml

> Источник фактов: целевая архитектура v2.6 (27.11.2026). Живой контракт; исходная версия сохранена в archive/spec-v2.6.md; «раздел N» и «приложение X» — номера v2.6, ссылка ↗ ведёт туда, где он теперь. Общая суть — [ARCHITECTURE.md](../ARCHITECTURE.md), связи — [GRAPH.md](../GRAPH.md), навигация — [INDEX.md](../INDEX.md).

**Зачем.** Весь конвейер описан файлами work-truth.git: роли, этапы, проверки, гейты, бюджет, сроки. Чтобы развернуть другое производство, меняются файлы, а не код. Один записываемый источник настроек.

**Владеет.** Формат workflow.toml (checks, review, merge, gate, budget, limits); routes.toml (харнессы, модели, аккаунты, fallback, проверенные версии); triggers.toml (cron, on_event); instructions/<роль>.md; правка через swarm workflow edit с ревизией.

**Вход.** swarm workflow edit владельца (демон пишет новую ревизию).

**Выход.** Task хранит последнюю применённую workflow_rev; новая версия применяется на следующем переходе по правилу ниже.

**Инварианты.**
- Прямая правка файла в work-truth.git не читается (видна сверке и отклоняется).
- Если workflow.toml или routes.toml берут на себя часть настроек, старые настройки удаляются в том же шаге.
- workflow.toml настраивает поддерживаемый конвейер; произвольного движка нет.
- Скрипт подготовки (setup) с изменённым sha256 без новой ревизии не запускается.

**Зависит от.** [store.md](store.md) (work-truth.git), [task-controller.md](task-controller.md).

**Статус.** Значения стартовые, допущение.

### Work-truth.git

```
tasks/<id>/task.md      исходный запрос владельца, цель, критерии, область записи, ограничения, ревизия
tasks/<id>/journal.md   заметки передачи с источником: что сделано, что дальше, что не сработало
instructions/<роль>.md  инструкции ролей и правила проекта
workflow.toml           этапы, проверки, gate, политика ревью и merge
routes.toml             харнессы, модели, аккаунты, приоритеты
```

Отдельный репозиторий, а не .swarm/tasks в ветке проекта: агент не испортит задачу своим коммитом, задачи не утекают в публичный репозиторий, история задач не засоряет историю кода. Нынешнее хранение (work\_truth.rs: один коммит без родителя, журнал обрезается на 128 КиБ) переходит на ревизии с историей; захват индекса, детекторы секретов (work\_truth.rs:533-604) и страж репозитория (work\_truth\_repo.rs:100-194) берутся из него. Нынешний индекс git\_work\_tasks уже хранит ревизии поручений по агенту и поколению, но не модель ready, claimed, accepted и Attempt: её добавляем (раздел 5 [↗](task-controller.md)).

Настройки: один записываемый источник. Сейчас это config.toml и settings.\*; если workflow.toml и routes.toml берут на себя часть настроек, соответствующие настройки удаляются в том же шаге, иначе появятся две правды.

Проверки — просто команды в workflow.toml, без Rust-кода на каждый линтер. Там же гейты ручного режима, сроки и бюджет (значения стартовые, допущение). workflow.toml настраивает поддерживаемый конвейер (проверки, роли, gates); произвольно программировать любой граф работы он не умеет, и это отдельная функция со своей ценой.

```toml
[checks.rust]
run = "cargo clippy --locked -p {crate} -- -D warnings"

[review]
enabled = true                # политика проекта, а не обязательство каждой задачи
reviewer = "other-family"     # другая семья моделей, если доступна

[merge]
mode = "squash"

[gate]                         # auto | owner
claim = "auto"                 # старт задачи
replace_executor = "auto"      # замена исполнителя
accept_review = "auto"         # принять вердикт ревью
merge = "auto"                 # push main
cleanup = "auto"               # удаление веток и worktree
deploy = "owner"
analysis_verdict = "auto"      # вердикт разбора
budget_extend = "owner"        # только владелец увеличивает общий бюджет; auto здесь недопустим

[budget]                       # общий конечный лимит Task, все роли и повторы вместе, не размер возобновляемой порции
attempts = 6
wall_hours = 8
usd = "unknown"                # число или "unknown" (подписка): тогда предел задают попытки и время

[limits]
turn_max_min = 60
tool_max_min = 20
claim_ttl_min = 10
check_ttl_min = 30
review_ttl_min = 120
integrate_ttl_min = 30
held_ttl_min = 240
```

Весь конвейер описан файлами work-truth.git (идея WORKFLOW.md из Symphony): роли, этапы, проверки, гейты, политика ревью и merge. Чтобы развернуть другое производство — документацию, данные, — меняются workflow, роли и проверки, а не код.

## Смена workflow (раздел 14)

Task запоминает `workflow_rev`, по которой был принят последний переход. `swarm workflow edit` создаёт новую ревизию; она применяется к активной задаче при следующем переходе, включая admission `IntegrationStep planned → sending`. Старая версия не закрепляется молча до конца задачи.

Перед переходом Store обновляет применённую ревизию и заново проверяет затронутые разрешения. Открытый Gate по изменённой политике становится superseded; принятое решение остаётся в истории и не даёт допуска изменённому действию. Новые checks/review требуют соответствующего результата. Уже выполненный CheckRun остаётся историческим фактом, а его пригодность определяется совпадением Candidate и замороженной конфигурации проверки. Одна смена режима не доказывает повторную проверку кода.

Если на admission planned → sending прежних допусков уже недостаточно, эффект не отправляется: planned-шаг отменяется, `step_rejected(reason = policy_changed)` возвращает Task в checking. Контроллер сохраняет пригодные CheckRun и получает недостающие проверки/ревью и Gate; новый шаг создаётся через обычную очередь. Это не повод запускать исполнителя заново.

Шаг, принятый в sending, хранит прежнюю неизменную привязку; поздний запрет пишется как намерение и учитывается при сверке, не отменяет внешнюю операцию задним числом. Транзакция Store и push не атомарны; граница задана в [integrator.md](integrator.md#журнал-шагов). Ручная правка файлов мимо демона не применяется.

Увеличение общего бюджета всегда требует конкретного решения владельца; `budget_extend = auto` отклоняется при проверке workflow. Автоматический режим работает внутри уже выделенного лимита. Деление бюджета между дочерними Task сохраняет общий остаток, а не создаёт новый лимит; отдельный механизм автоматически пополняемых порций не вводится.

## Триггеры (раздел 11а)

### Триггеры: расписание и события

Старые правила и таймеры возвращаются в минимальном виде: triggers.toml в work-truth.git, два вида. cron — создать Task из шаблона по расписанию; on\_event — на Event заданного вида с фильтром по полям создать Task или отправить сообщение. Скриптового движка нет: действие триггера — только создание Task или сообщение, всё остальное делает обычный конвейер. Триггер с ошибкой отключается и даёт уведомление.

## Шаги подготовки (раздел 11а)

- Шаги подготовки рабочего места (setup) фиксируются в workflow с sha256 скрипта; изменённый скрипт без новой ревизии не запускается.
