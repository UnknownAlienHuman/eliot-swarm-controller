# Forge-плагин GitHub

> Источник фактов: целевая архитектура v2.6 (27.11.2026). Живой контракт; исходная версия сохранена в archive/spec-v2.6.md; «раздел N» и «приложение X» — номера v2.6, ссылка ↗ ведёт туда, где он теперь. Общая суть — [ARCHITECTURE.md](../../ARCHITECTURE.md), связи — [GRAPH.md](../../GRAPH.md), навигация — [INDEX.md](../../INDEX.md).

**Зачем.** GitHub нужен только интегратору: push веток и main, PR, ruleset, выдача короткоживущих токенов, чтение check runs внешнего CI. Для старта и работы задачи до кандидата GitHub не нужен.

**Владеет.** Токены установки GitHub App (на один репозиторий, 1 час); процесс forge-push; ruleset на main с обходом только для GitHub App Swarm; поиск PR по head-ветке перед созданием; CheckRun с source = ci.

**Инварианты.**
- Токен forge есть только у forge-push; агенты и интегратор-актор его не держат.
- Push ветки: --force-with-lease с ожидаемым SHA, перед повтором ls-remote; push main только fast-forward на проверенный OID.
- Force-push и удаление main запрещены всем.
- Сверка видит на remote SHA, которого интегратор не отправлял, и поднимает тревогу.

**Зависит от.** [integrator.md](../integrator.md), [security.md](../security.md).

**Статус.** Против настоящего GitHub не проверено (этап 5: «push в main чужим токеном отклонён»); поиск по маркеру под нагрузкой GitHub не проверен.

## Токен и push (раздел 4)

- Токен forge есть только у процесса forge-push. Это короткий процесс, который получает от интегратора команду «отправить такой-то OID в такую-то ветку» и выходит. Токен — токен установки GitHub App на один репозиторий, живёт 1 час. Закрытый ключ App лежит у отдельной учётной записи ОС, от которой запускается только forge-push; процесс демона и агенты его не читают. Интегратор-актор токена не держит. Агенты токена не видят: в их окружении его нет.

- Push агентов. Worktree делят refs и конфигурацию репозитория, поэтому недействительный pushurl и отключённый помощник учётных данных — не неизменяемый запрет для агента с shell. Настоящий барьер — отсутствие токена у агента, ruleset на main с обходом только для GitHub App Swarm и GitHub push protection; сверка видит на remote SHA, которого интегратор не отправлял.

## Идемпотентность внешних шагов (раздел 6)

### Идемпотентность внешних шагов

- push ветки: --force-with-lease=<ветка>:<ожидаемый SHA>; перед повтором ls-remote.
- push main: только fast-forward на проверенный OID; после потери ответа — проверка достижимости.
- PR: перед созданием ищем PR по head-ветке (так уже делает publication.rs:1455 перед 826).
- merge: доказательство — достижимость итогового IntegrationStep.new_oid из origin/main; Candidate.commit остаётся исходным OID.
- deploy: только через плагин с ключом (задача, OID); плагин сначала читает версию на цели; компенсация — предыдущая версия.
- API без ключа идемпотентности: маркер в теле объекта, поиск по маркеру перед повтором (предложение, поведение поиска GitHub под нагрузкой не проверено).

## Ruleset (раздел 14)

Main защищён ruleset: прямой push в main может делать только GitHub App Swarm как bypass actor; force-push и удаление main запрещены всем. Это пункт этапа 5 с критерием «push в main чужим токеном отклонён».

## Защита main от облачных агентов (раздел 10а)

### Защита main от облачных агентов

Облачный агент пушит своим токеном провайдера, а не нашим, поэтому «у агента нет токена» здесь не работает. Барьер — правила GitHub на стороне remote: ruleset на main, в котором обходить запрет может только GitHub App Swarm (интегратор), а запрет force-push и удаления действует для всех. Пока такого ruleset нет, облачный плагин для репозитория не включается: демон проверяет ruleset через API при включении плагина и раз в сутки. Сверка (раздел 3 [↗](../daemon.md), инвариант 4) остаётся вторым рубежом и ловит то, что прошло мимо правил.

## Внешний CI (раздел 11а)

- Внешний CI: forge-плагин читает check runs GitHub по запушенному кандидату в CheckRun с source = ci; workflow может требовать их как обязательные.
