Этот документ — запрошенный снимок проекта, а не новая система статусов. Roadmap — единственный канонический список статуса функций и порядка работ. Ограничения и открытые инженерные проблемы отслеживаются в issue #384; история исправления ошибки наблюдения и runtime evidence — в PR #383.

## Краткий вывод

В репозитории собран связный контроллер локальных coding-agent harness: один Rust CLI и daemon принимают команды, маршрутизируют их через общий API и плагины, сохраняют состояние в SQLite и публикуют зафиксированные события. Реализованы пять native adapters, наблюдение процессов и Git, управляемые workspaces, правила и таймеры, ограниченные scripts и Eliot-mode Goals, очередь mail, CAS-переменные, иерархия Agent, локальный MCP и облачный MCP-вход. Неизвестное состояние и неопределенный результат внешнего эффекта сохраняются явно; повторять неопределенный prompt или side effect нельзя.

Roadmap отмечает L0–L6 выполненными и физическую retention-очистку из L7 реализованной. Это говорит о доставленных путях в исходниках и выбранной области фич, а не о квалификации полного продукта. Семь оставшихся широких проверок L7 — end-to-end, сбои на границах commit/effect, реальные маршруты harness, автоматизация и recovery, custody платформ, retention/backpressure и целевая нагрузка — остаются открытыми. Поэтому проект ещё нельзя называть полностью квалифицированным или feature-complete.

Путь Codex Observer исследован, но корневая причина SQLite initialization failure не установлена. По текущему контракту выбор native store и witness проверяется на двух стадиях, поэтому нужны два обычных старта; повторное использование probe-процесса и неявная смена приоритета переменной окружения признаны небезопасными. Исходники и конфигурация Codex не менялись. Активные ограничения этого пути отслеживаются в issue #384.

## Как устроен работающий путь

Архитектура намеренно имеет один путь записи и один путь команд: CLI, Agent или автоматизация обращаются к daemon API; Router валидирует principal, поколение, turn/request bindings и verb; plugin host выполняет native effect; Store фиксирует событие и проекцию до публикации в event bus. Ядро — чистые типы и reducer без I/O; Store владеет SQLite и одним writer; плагины переводят типизированные сообщения в протокол конкретного vendor. Автоматизация и coordination вызывают тот же Router, а не отдельный executor. Контракт изложен в [architecture](../architecture.md), [core spec](../spec/core.md), [API spec](../spec/api.md) и [plugin protocol](../spec/plugin-protocol.md).

Команды проходят состояния accepted/queued/dispatched и затем applied, rejected, failed или unknown. После dispatch транспортная ошибка сама по себе не доказывает отсутствие native effect: неизвестный результат остается unknown и не запускается повторно. Для повторов используется прежний mutation ID и тот же payload. Агент, поколение, активный turn, native request, источник событий и границы истории остаются связаны точными идентификаторами. Успешная регистрация observation не превращает observe-only Agent в управляемый и не делает неизвестное native состояние «idle». Это ключевая причина, по которой часть сбоев требует точного readback, а не автоматического retry.

В публичном CLI есть launch/send/watch/result/stop/resume, чтение состояния и событий, правила и таймеры, Goal-команды, диагностика процессов, bounded history, observe attach/detach, работа с workspace, mail, переменными и MCP. Профиль выбирает конкретный harness и модель; автоматической подстановки модели, аккаунта или fake runtime нет. Не подключенные или неподдерживаемые semantics должны возвращать unsupported, а не имитировать более слабую операцию.

## Нагрузка и открытые ограничения

Roadmap остаётся единственным каноническим списком статуса функций; issue #384 отслеживает активные ограничения и открытые инженерные проблемы. Измерения ниже фиксируют конкретные сценарии:

* Реальный четырёх-reader metadata workload записал 7 590 event rows в 54 точных summary-интервалах за 600 секунд. Один интервал с gap/watermark был исключён. Первый полный интервал: 157 rows за 11,56 секунды, то есть 13,5813 rows/s; CPU — 31,74% одного ядра, peak RSS — 58 490 880 байт. Это пропускная способность данного сценария, не максимальная ёмкость единственного Store writer.
* Тот же реальный replay на 60 000 событий, 60 страниц и 23 382 203 JSON bytes дал два клиентских замера. PowerShell-вариант занял 43,147 секунды (1 390,59 событий/с) и включал per-event validation, byte tally, SHA-256, 120 Core identity checks и работу клиента. Оптимизированный C# consumer обработал те же bytes и digest за 1,567398 секунды — 38 280 replay events/s, примерно 27,5× быстрее клиентского результата PowerShell. Stop cursor и digest совпали, gap не было; cap остановил частичный prefix до pinned high-water. C# убрал per-event bottleneck PowerShell-клиента. Full-read занял 1 002,792 ms; зафиксированы first-byte 924,344 ms, parse 321,889 ms, validation 53,911 ms и digest 16,743 ms. CPU consumer 1,375 s, MCP 0,4375 s и Core 1,0156 s получены одновременно, attribution между ними изолировать нельзя. Это только replay/read, не ingress/commit throughput и не qualification 10k/8/2k.
* Одна отдельная страница на 1 000 events дала 28,181 ms до первого байта, 31,535 ms до полного ответа, 14,285 ms на decode и 12,905 ms на validation; полное измерение flush-to-validation — 79,365 ms. Один page-run не задаёт устойчивую latency или узкое место Store/daemon.
* Целевой сценарий 9 992 settled histories плюс восемь одновременно активных native tasks, как и ориентир 2 000 новых events/s, не запускался. Восемь task inputs подготовлены, но задачи остаются unqualified. Нельзя объявлять цель достигнутой по replay-скорости или числу уже зарегистрированных histories.

Путь Codex Observer исследован, но корневая причина SQLite initialization failure остаётся Unknown. В Captured profile значение CODEX_SQLITE_HOME уступает native config sqlite_home; hashed native_scope/store binding нельзя декодировать обратно в доверенный путь. Literal NativeStoreBinding допустим только как вход контролируемого launch, не observer attach. Текущий precedence/witness contract требует два обычных старта — probe и pinned reader; повторное использование probe и неявный env-over-config приоритет небезопасны. В трёх попытках native startup metadata не вернулась из-за SQLite state initialization; сохранённая ошибка не различает probe и pinned reader. Read-only quick_check прошёл, свободного места было достаточно, но inner SQLite/OS cause не установлена. Issue #384 отслеживает необходимость структурированной причины и точного указания стадии отказа.

Остаются также непроверенными Dot и отрицательные cloud-auth cases, Linux/Docker runtime custody, нормальная последовательность detach/drain для всех путей, полный crash/recovery matrix и retention/WAL/backpressure под репрезентативной нагрузкой. CI и компиляция полезны для статической корректности выбранного пакета; они не доказывают native effects, доставку сообщения, выход процесса или capacity. В рамках подготовки этого отчёта тестовые циклы, сборки и native calls не запускались.

## Что означает статус на эту дату

Наиболее точная формулировка такова: **основные продуктовые контуры L0–L6 реализованы; отдельные реальные маршруты работают; полная квалификация L7 не завершена**. Система уже пригодна для ограниченной работы через явно настроенные профили и умеет сохранять важную неопределённость. Пользователю следует считать unsupported каждую незаявленную возможность, а состояние liveness — только свидетельством жизни процесса, пока не видны native turn/event receipts.
